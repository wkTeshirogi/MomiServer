    Git基盤内蔵化・Git専用通知 方針決定メモ 2026/10/17¶

    サマリ¶

    MomiServerのGit基盤は、GitLabを恒久的な内部依存として残す方式ではなく、Gitリポジトリ管理、Git通信、CI/CD、GitHub連携およびバックアップをMomiServerへ段階的に内蔵する方針とする。

    CI/CD設定はMomiServerの管理画面を正規の編集手段とし、リポジトリ作成時に主要言語、利用する検査、実行契機および定期実行の有無を選択できるようにする。画面入力はバージョン付きの構造化設定として保存し、Pipeline実行時には変更不能な実行スナップショットへ変換する。

    既存のGitLab CI/CD定義は移行資産として解析・取り込みに利用する。ただし、GitLab CI形式のファイルをMomiServer運用後の正本にはせず、完全互換も初期目標としない。

    Git関連のDiscord通知は、既存の監視・セキュリティ・業務通知とは通知設定および通知先を分離する。CI/CDの開始・正常終了・エラー終了と、mainブランチへのマージ完了を主な通知対象とする。

    CI/CD設定管理方針¶

    設定の正本¶

    CI/CD設定の正本はMomiServerが保持するバージョン付き構造化データとし、管理画面を正規の編集手段とする。リポジトリ内の設定ファイルを直接解釈して自動的にサーバ設定を変更する方式は採用しない。

    設定変更時には、変更前後の差分、変更者、変更日時および変更理由を記録する。Pipeline開始時には、使用するCI/CD設定、言語テンプレートのバージョン、実行コンポーネントのバージョンおよびSecret参照を実行スナップショットとして確定する。後から設定が変更されても、過去のPipelineがどの条件で実行されたかを再現できるようにする。

    画面管理によって可搬性が失われないよう、機密値を除いた設定のエクスポート、インポートおよび差分確認機能を将来対象とする。エクスポート形式はバックアップおよび監査用であり、通常運用時の編集経路にはしない。

    リポジトリ作成時の設定¶

    リポジトリ作成画面では、少なくとも以下を設定する。

    項目 内容
    主要言語 Java、JavaScript／TypeScript、Go、Python、ドキュメント等から選択する
    ビルド方式 Gradle、Maven、npm、pnpm、Go Modules等を主要言語に応じて候補表示する
    言語・ツールバージョン JDK、Node.js、Go等の実行バージョンを選択する
    CI/CDテンプレート 主要言語とビルド方式に対応する推奨テンプレートを選択する
    通常チェック ビルド、単体テスト、Lint、静的解析等の初期有効・無効を選択する
    定期チェック 定期検査全体の有効・無効と推奨セットを選択する
    実行環境 必要なAgent能力、コンテナイメージ、CPU、メモリおよびタイムアウトの既定値を選択する
    通知 失敗、復旧、main成功等のGit専用通知条件を選択する

    初期段階では主要言語を1つ選択する。複数言語を含むリポジトリへの対応は必要性を確認して別途要件化し、補助言語または複数プロジェクトルートを登録できる構造を検討する。

    主要言語はテンプレート選択の起点として利用するが、拡張子だけで実行内容を確定しない。既存リポジトリの取り込み時には構成を検出して候補を提示し、利用者の確認後に設定を保存する。

    CI/CD項目ごとの画面設定¶

    管理画面では、Pipeline定義ファイルを直接編集させず、以下の機能を項目単位で有効化および設定できるようにする。

    分類 項目例 主な実行契機
    ビルド コンパイル、成果物生成 MR、push、mainへのマージ後
    テスト 単体テスト、結合テスト MR、push、手動
    コード品質 Lint、SpotBugs、SonarQube MR、mainへのマージ後、定期
    セキュリティ FindSecBugs、依存関係、Secret、コンテナ検査 MR、依存関係変更時、定期
    サプライチェーン SBOM生成、ライセンス検査、署名 main、Release、定期
    配布 Package、Container Image、Release成果物 tag、Release、手動承認後

    各項目では、少なくとも以下を設定できるようにする。

    • 有効・無効
    • 実行契機
    • 対象branch、tagおよび変更パス
    • 使用するテンプレートまたは実行コンポーネントのバージョン
    • 実行環境と必要なAgent能力
    • タイムアウト、再試行および同時実行数
    • 成功・失敗の判定基準
    • Artifact、レポートおよびログの保持期間
    • Pipelineを失敗させるか、警告として継続するか
    • Git専用Discord通知の対象とするか

    任意コマンド入力は、標準テンプレートで対応できない場合の拡張機能として扱う。導入する場合も権限制御、承認、監査および分離実行を必須とし、リポジトリ作成時の標準設定には含めない。

    定期チェック¶

    定期チェックの有効・無効はリポジトリ作成時に選択でき、作成後もCI/CD設定画面から変更できるようにする。単一の全体スイッチだけではなく、チェック項目ごとに周期を設定可能とする。

    設定項目 内容
    有効・無効 定期チェック全体および個別項目の実行可否
    周期 日次、週次、月次または個別スケジュール
    実行日時 曜日、時刻およびタイムゾーン
    対象ref 原則として既定branchの最新commit
    重複時動作 前回実行を待つ、今回をスキップする、前回を中止する
    未実行時動作 サーバ停止等で逃した実行を再開後に補完するか
    結果判定 Pipeline失敗、警告または記録のみ
    結果通知 新規検出、悪化、復旧、実行エラー等の通知条件
    結果集約 専用ページ、Issue、Artifactまたはレポート履歴への反映

    初期テンプレートでは、SpotBugsおよびFindSecBugsをMR時、SonarQubeをmainへのマージ後、Dependency-Checkを依存関係変更時および週次の定期チェックとする案を既定値とする。ただし、ツール名をPipelineの制御単位にはせず、コード品質、静的セキュリティ解析、依存関係検査等の検査種別として管理する。

    定期チェックの結果は実行成否と検査結果を分離する。検査ツール自体の異常終了、脆弱性・品質問題の検出、前回から変化がない状態を区別し、同一内容を毎回通知しない。

    テンプレートと設定継承¶

    CI/CDテンプレートは、主要言語、ビルド方式および用途ごとにMomiServerが管理する。テンプレートには推奨チェック、実行順序、実行環境、キャッシュ、レポート形式および既定の判定基準を含める。

    設定はシステム、グループおよびリポジトリの順に継承できるようにする。リポジトリ画面では、各値がテンプレート、グループ既定値またはリポジトリ上書きのどこから適用されたかを表示する。

    テンプレート更新時は既存設定を自動上書きせず、影響、差分および移行可否を表示する。セキュリティ上の緊急更新を強制適用する仕組みを設ける場合は、対象範囲、猶予期間、例外承認および監査を別途設計する。

    GitLab CIからの移行¶

    初期実装では、現在のMomiServer関連リポジトリで使用している.gitlab-ci.ymlを調査し、画面設定へ変換可能な要素と個別対応が必要な要素を分類する。

    移行機能はGitLab CI定義を直接実行する互換エンジンではなく、解析結果をMomiServerのCI/CD項目へ対応付けるインポート支援として実装する。対応できない条件、独自スクリプトおよび外部サービス依存は警告として表示し、利用者が変換結果を確認してから保存する。

    GitLab固有変数は必要に応じて移行候補へ対応付けるが、MomiServer上のSecretまたは実行コンテキストへ無条件にコピーしない。

    GitHub連携先設定¶

    設定単位¶

    GitHub連携先は、以下の単位で設定できるようにする。

    設定単位 用途
    システム GitHub連携全体の既定値。未設定も許容する
    グループ グループ配下のリポジトリに適用する既定値
    リポジトリ 特定リポジトリだけに適用する上書き値

    有効な設定は、リポジトリ、最も近い親グループ、上位グループ、システムの順に解決する。上位設定を継承するか、連携を無効化するか、別の連携先へ上書きするかを明示的に選択できるようにする。

    管理画面では設定値だけでなく、継承を解決した後の有効値と、その値がどの階層で設定されたかを表示する。

    連携用途¶

    リポジトリは、用途ごとに複数のGitHub連携先を持てるようにする。

    用途 想定Visibility 同期内容
    非公開バックアップ private 許可した全branch、tagおよびGit履歴
    公開ミラー public 公開を許可したbranch、tagおよびGit履歴
    Release公開 publicまたはprivate Release成果物、チェックサム、リリースノート

    非公開バックアップと公開ミラーを同じGitHubリポジトリへ切り替えて使用する運用は原則として採用しない。公開範囲の誤設定を防ぐため、用途ごとに別の連携設定と監査記録を持つ。

    GitHubパスの表現¶

    GitHub上のリポジトリは、自由入力されたURL文字列ではなく、以下の構造で管理する。

    • GitHub接続先ID
    • GitHub Owner種別
    • GitHub Owner名
    • GitHubリポジトリ名
    • 用途
    • Visibility
    • 同期対象ref
    • 有効・無効

    GitHubにはMomiServerのグループ階層をそのまま格納するリポジトリパスがないため、グループ設定ではGitHubリポジトリ名の生成規則を指定できるようにする。

    生成規則の候補は以下とする。

    • リポジトリ名をそのまま使用する
    • グループ名を接頭辞として付与する
    • MomiServer上のグループパスを区切り文字で連結する
    • リポジトリ単位で固定名を指定する

    生成後のGitHub Owner名とリポジトリ名の組み合わせが重複する場合は、作成または設定保存を拒否し、明示的な上書きを要求する。

    設定項目案¶

    項目 内容
    連携用途 非公開バックアップ、公開ミラー、Release公開
    継承方式 親設定を継承、無効化、個別設定
    GitHub接続先 GitHub Appのインストール先を参照するID
    GitHub Owner UserまたはOrganizationの名前
    リポジトリ名規則 グループ既定の名前生成規則
    固定リポジトリ名 リポジトリ単位の明示的な名前
    Visibility privateまたはpublic
    同期対象 全ref、protected branch、指定branch、tag
    同期契機 push後、Release作成後、定期照合、手動実行

    公開前検査 Secret、内部情報、ライセンスおよび履歴の検査

    GitHubの認証情報そのものをグループまたはリポジトリ設定へ保存せず、別途安全に管理するGitHub接続先をIDで参照する。GitHub Appを第一候補とし、個人のPersonal Access Tokenへの恒常的な依存を避ける。

    設定変更時の扱い¶

    GitHub Owner、リポジトリ名または用途を変更しても、既存GitHubリポジトリの移動、名前変更または削除は自動実行しない。変更後の連携先を検証し、初回同期の影響を表示した上で、管理者の承認後に切り替える。

    連携解除時もGitHubリポジトリは自動削除せず、MomiServerからの同期だけを停止する。GitHub側の削除は独立した高リスク操作として扱う。

    Git専用Discord通知¶

    分離方針¶

    Git専用Discord通知は、既存の監視・セキュリティ・業務通知とは以下を分離する。

    • 有効・無効設定
    • Webhook URL
    • 通知先チャンネル
    • イベント種別
    • メッセージテンプレート
    • 再試行状態
    • 通知履歴
    • レート制御

    Discord WebhookへHTTPリクエストを送信する低レベル処理は共通部品として再利用可能とするが、Gitイベントの判定、メッセージ生成、通知先解決および配信状態管理はGit通知機能の責務とする。

    通知イベント案¶

    イベント種別 発生条件 通知タイミング 初期重要度
    git_pipeline_started CI/CD Pipelineの実行開始 実行状態を保存した後 info
    git_pipeline_succeeded Pipelineが正常終了 最終結果を保存した後 success
    git_pipeline_failed Job失敗等によりPipelineがエラー終了 最終結果と失敗Jobを保存した後 error
    git_pipeline_cancelled 利用者またはシステムがPipelineを中止 最終結果を保存した後 warning
    git_pipeline_timed_out PipelineまたはJobがタイムアウト 最終結果を保存した後 error
    git_main_merge_completed 変更がマージ操作によってmainへ反映 ref更新と監査記録の確定後 success

    開始・正常終了通知をすべてのbranchで有効にすると通知量が増えるため、リポジトリ単位またはbranch単位で通知対象を設定できるようにする。エラー終了およびmainへのマージ完了は、初期状態で通知対象とする案を優先する。

    通知内容案¶

    通知には以下の情報を含める。

    • リポジトリ名
    • Pipelineまたはマージのイベント種別
    • 実行状態
    • 対象branchまたはtag
    • 対象commitの短縮SHA
    • 起動者またはマージ実行者
    • 開始日時および終了日時
    • 実行時間
    • 失敗したJob名と要約
    • MomiServer上のPipeline、commitまたはマージ結果へのリンク

    通知本文には、Personal Access Token、CI/CD Secret、Webhook URL、環境変数の機密値、Jobログ全文を含めない。エラー内容は調査開始に必要な要約に限定し、詳細ログはMomiServer上で認証後に参照する。

    配信制御案¶

    • Gitイベントと通知イベントを同一トランザクションまたはOutbox方式で対応付ける。
    • 通知イベントごとに一意なIDを付け、再送時の重複を識別できるようにする。
    • Discord送信は非同期処理とし、Pipelineやマージ処理を待機させない。
    • 一時的な送信失敗は再試行し、上限到達後は失敗状態として保持する。
    • Webhookの無効化、認証失敗およびDiscord側レート制限を区別して記録する。
    • 同一Pipelineについて、終端状態の通知を複数回送らない。
    • 通知の有効・無効、送信先変更および手動再送を監査ログへ記録する。

    初回着手範囲¶

    決定内容¶

    初回着手はPhase 0の要件・設計・技術検証全体とし、本実装はJGitによるGit Smart HTTPの技術検証までに限定する。Gitリポジトリ基盤MVP、CI/CD、GitHub連携、マージ・レビューおよび実イベント通知は、前段の完了条件を確認してから個別に着手を判断する。

    この区切りは、Git通信、認証・認可、ストレージおよび復旧方式の成立を確認する前に、CI/CDや外部連携の実装を積み上げることを避けるために設ける。

    ストレージ設計 DBメタデータとbare repositoryの対応、保存先、容量制限、論理削除および復元の設計
    セキュリティ設計 PAT、read・write・admin権限、branch保護、Secret境界および監査の設計
    バックアップ設計 Gitリポジトリとメタデータのバックアップ単位、復元順序およびcommit SHA照合の設計・検証
    画面要件 Git管理画面と画面管理型CI/CDの入力項目、設定履歴および権限制御の定義
    通知設計 Git専用通知設定、イベント形式、Outbox、再試行、重複防止および監査境界の定義

    今回実装しない機能¶

    • Gitリポジトリ管理画面およびGitサーバの本番実装
    • SSHによるGit通信およびSSH公開鍵管理。当面の実装予定は設けず、HTTPSで解決できない要件が発生した場合に再評価する
    • Git LFS
    • CI/CDジョブ実行およびCI/CD設定画面
    • GitHubへのバックアップ、公開ミラーおよびRelease公開
    • Pull Request相当のマージ要求、レビューおよび承認
    • Pipeline開始・終了通知およびmainへのマージ完了通知
    • Issue、Wiki、Package RegistryおよびContainer Registry

    通知設定とイベント境界は今回設計するが、Pipeline通知はCI/CD実装時、mainへのマージ完了通知はマージ・レビュー基盤の実装時に追加する。単純なmainのref更新をマージ完了として扱わない。

    次フェーズへの移行条件¶

    Gitリポジトリ基盤MVPの実装へ進むには、少なくとも以下を満たす必要がある。

    • 初期対象と対象外機能が要件として確定している。
    • JGitで認証付きのclone、fetchおよびpushを実行できる。
    • 権限違反、force push、branch削除等をGit ref更新前に拒否できる見通しがある。
    • 同時pushおよび通信中断後もリポジトリ整合性を維持できる。
    • バックアップから別領域へ復元し、全対象refのcommit SHAが一致する。
    • MomiServer BackendとAgentの責務境界が確定している。
    • セキュリティ境界、監査対象、Secret管理および復旧手順を説明できる。

    実装フェーズ¶

    実装は以下のフェーズに分割する。各フェーズは、前段の完了条件を満たした後に着手する。既存GitLabからMomiServerへの正本切替は、必要機能と復旧手順が揃うまで実施しない。

    Phase 0 要件・設計・技術検証¶

    Phase 0の実施内容¶

    • FR-0054からFR-0056をMomiServer内蔵Git基盤の要件として具体化する。
    • GitHub連携、画面管理型CI/CD、言語別テンプレート、定期チェックおよびGit専用通知を独立した機能要件として定義する。
    • Git Smart HTTP、ストレージ、認証・認可、監査およびバックアップの基本設計を作成する。
    • 現行.gitlab-ci.ymlで使用しているジョブ、実行条件、変数、レポートおよび外部依存を全対象リポジトリから抽出し、画面設定項目との対応表を作成する。
    • リポジトリ作成画面、CI/CD設定画面、定期チェック設定画面および設定変更履歴画面の要件を定義する。
    • Java、JavaScript／TypeScript、Go、Pythonおよびドキュメント用テンプレートの初期範囲を決定する。
    • Java用Git実装とSpring Bootの組み込み方式を検証する。
    • bare repositoryの作成、clone、fetchおよびpushを行う最小構成の技術検証を実施する。
    • CIジョブをMomiServer Agentの分離環境で実行できることを検証する。

    Phase 0の完了条件¶

    • 要件定義、基本設計、主要機能の詳細設計が順番に作成されている。
    • 初期対応するGit機能と対象外機能が確定している。
    • CI/CD設定モデル、画面項目、テンプレート初版およびGitLab CIからの移行対象が確定している。
    • Git Smart HTTPとAgent実行方式に実装上の重大な阻害要因がない。
    • セキュリティ境界、バックアップ単位および復旧方式が説明できる。

    Phase 1 Gitリポジトリ基盤¶

    Phase 1の実施内容¶

    • リポジトリの作成、参照、更新、論理削除および復元を実装する。
    • bare repositoryとDB上のメタデータを内部IDで対応付ける。
    • HTTPSによるclone、fetch、pullおよびpushを実装する。
    • Personal Access Tokenの発行、検証、失効およびスコープ制御を実装する。
    • リポジトリ単位のread、writeおよびadmin権限を実装する。
    • branch、tag、commitおよびref更新履歴の参照機能を実装する。
    • protected branch、force push禁止、branch削除禁止およびtag上書き禁止を実装する。
    • Git操作の監査ログを実装する。
    • リポジトリ容量制限、pushサイズ制限およびタイムアウトを実装する。
    • Gitリポジトリとメタデータのバックアップ・復元を実装する。

    Phase 1の完了条件¶

    • 標準Gitクライアントから認証付きclone、fetch、pullおよびpushが成功する。
    • 権限のない操作と保護規則に反するpushが拒否される。
    • 同時push、異常切断および容量超過時にリポジトリが破損しない。
    • 監査ログから操作主体、対象リポジトリ、refおよび結果を追跡できる。
    • バックアップから別の検証環境へ復元し、commit SHAが一致する。

    Phase 2 CI/CD設定・実行基盤¶

    Phase 2の実施内容¶

    • バージョン付きCI/CD設定モデル、Validator、変更履歴および実行スナップショットを実装する。
    • リポジトリ作成時の主要言語、ビルド方式、通常チェックおよび定期チェックの選択を実装する。
    • CI/CD項目ごとの有効・無効、実行契機、判定基準、実行環境、保持期間および通知条件の管理画面を実装する。
    • Java、JavaScript／TypeScript、Go、Pythonおよびドキュメント用テンプレートの初版を実装する。
    • テンプレートのバージョン管理、適用元表示、更新差分および明示的な更新操作を実装する。
    • .gitlab-ci.ymlの解析結果を画面設定へ対応付ける移行支援を実装する。
    • Pipeline、Stage、Job、依存関係および状態遷移を実装する。
    • push、branch、tag、マージ、定期スケジュールおよび手動操作によるPipeline起動を実装する。
    • 定期チェックの重複制御、未実行時の扱い、結果履歴および差分通知を実装する。
    • MomiServer AgentのRunner登録、能力情報、Job取得および実行制御を実装する。
    • 分離されたコンテナ実行、services、タイムアウト、キャンセルおよび後処理を実装する。
    • Jobログのストリーミング、保存、マスキングおよび参照を実装する。
    • Artifact、JUnitレポート、Cacheおよび保持期限を実装する。
    • PipelineとJobの再実行およびキャンセルを実装する。
    • CI/CD開始、成功、失敗、中止およびタイムアウトのGit専用Discord通知を実装する。

    Phase 2の完了条件¶

    • 現行Java、React、Goおよびドキュメント用CI/CDの対象処理を画面設定から実行できる。
    • 設定の保存前に不整合が明示され、過去のPipelineから使用した設定スナップショットを確認できる。
    • リポジトリ作成時に選択した主要言語から推奨チェックが展開され、利用者が項目ごとに変更できる。
    • 定期チェックが指定日時に実行され、同一結果の重複通知を抑制できる。
    • Agent障害、Jobタイムアウトおよびキャンセル後に一時実行環境が残留しない。
    • Jobログへ登録済みSecretがそのまま出力されない。
    • Pipeline終端状態、テスト結果およびArtifactをMomiServerから参照できる。
    • Git専用Discord通知の重複防止と失敗時再試行を確認できる。

    Phase 3 GitHub連携¶

    Phase 3の実施内容¶

    • GitHub接続先とGitHub App連携を実装する。
    • システム、グループおよびリポジトリ単位の設定継承を実装する。
    • 非公開バックアップ、公開ミラーおよびRelease公開を別モードとして実装する。
    • GitHub Owner、リポジトリ名生成規則、固定名および重複検査を実装する。
    • GitHubリポジトリの自動作成を実装する。
    • push後の非同期同期、定期照合、手動同期および再試行を実装する。
    • MomiServerとGitHubのrefおよびcommit SHAの一致確認を実装する。
    • 公開前のSecret、内部情報、ライセンスおよびGit履歴検査を実装する。
    • 連携先変更時の影響確認と管理者承認を実装する。

    Phase 3の完了条件¶

    • グループ既定値とリポジトリ上書きを意図どおり解決できる。
    • 非公開バックアップと公開ミラーを別のGitHubリポジトリへ同期できる。
    • GitHub障害時も元のGit pushとCI/CDが正常に完了する。
    • 同期失敗、不一致、認証失敗および再試行状態を確認できる。
    • publicへの変更と初回公開同期が管理者の明示的承認なしに実行されない。
    • 連携解除によってGitHub側のリポジトリが削除されない。

    Phase 4 マージ・レビュー基盤¶

    Phase 4の実施内容¶

    • branch間の差分、commit一覧および競合状態を表示する。
    • Pull Request相当のマージ要求を作成、更新、承認および却下できるようにする。
    • レビューコメント、承認数および変更要求を管理する。
    • 必須CI/CD結果とbranch protectionをマージ条件へ統合する。
    • merge commit、squashおよびfast-forwardの対応範囲を定義して実装する。
    • mainブランチへのマージ完了イベントを確定し、Git専用Discord通知を実装する。
    • マージ操作と承認操作を監査ログへ記録する。

    Phase 4の完了条件¶

    • 保護されたmainへ直接pushせず、承認済みマージ要求から変更を反映できる。
    • 必須CI/CDが失敗または未完了の場合にマージできない。
    • 同一マージについて完了通知が一度だけ送信される。
    • マージ元、マージ先、実行者、承認者および反映commitを追跡できる。

    Phase 5 GitLab移行・正本切替¶

    Phase 5の実施内容¶

    • GitLab上の全対象リポジトリをMomiServerへmirror移行する。
    • branch、tag、commit、既定branchおよびリポジトリ容量を照合する。
    • CI/CD VariablesとSecretを安全な移行手順で再登録する。
    • GitLab CI/CDとMomiServer CI/CDの比較実行を行う。
    • 利用者のGit remoteをMomiServerへ切り替える。
    • 切替期間中のGitLabをread-onlyとする。
    • GitHub連携の実行主体をGitLabからMomiServerへ切り替える。
    • 復旧条件、切戻し条件およびGitLab停止条件を確認する。

    Phase 5の完了条件¶

    • 全対象refのcommit SHAがGitLabとMomiServerで一致する。
    • 必須CI/CDがMomiServer上で成功する。
    • 利用者とAgentがMomiServerを正本として動作する。
    • GitHubバックアップまたは公開連携がMomiServerから実行される。
    • 切戻し手順を検証済みである。
    • 合意した保持期間中に重大な欠落が見つからない。

    GitLabは上記完了条件を満たし、最終バックアップを取得した後に停止する。停止と削除は分離し、停止直後にデータを削除しない。

    実施候補¶

    • Git LFS
    • Issue管理
    • Wiki
    • Release管理の拡張
    • Package Registry
    • Container Registry
    • Webhook
    • 外部IDプロバイダー連携
    • 高可用性およびストレージ分散

    Phase 6の各機能は一括実装せず、利用目的、運用負荷および既存サービスで代替できない理由を確認して個別に要件化する。 SSHによるGit通信はPhase 6の実施候補にも含めず、HTTPSで解決できない具体的要件が発生した場合にのみ候補へ追加する。

    フェーズ共通の実装原則¶

    • 各フェーズで要件定義、基本設計、詳細設計、実装、テストおよび運用確認の順序を守る。
    • Gitリポジトリ、CI/CDおよびSecretを扱う機能は、正常系だけでなく権限違反、異常切断、再試行、同時実行および復旧を確認する。
    • Backendは任意のCIジョブを自身の権限で直接実行せず、Agentの分離された実行環境へ委譲する。
    • GitHub、DiscordおよびAgentの外部障害によって、確定済みのGit操作またはCI/CD結果を巻き戻さない。
    • データ削除、公開範囲拡大、連携先変更および正本切替は、影響確認と明示的承認を必要とする。
    • フェーズ完了時にはバックアップと復元を含む検証証跡を残す。
