## 異常系・残対応

以下は初回調査時の指摘。2026/10/31時点の対応状況は末尾の追記を正とする。

### PG-01: 取得失敗を正常な0件として表示する

- 区分: 要修正。優先度: 高。
- ユーザー・サービス・端末の主APIを503にすると、取得完了後に検索結果0件となり、取得失敗の通知が出ない。
- 生成クライアントは標準では例外ではなくerrorを返すが、これらの呼出元はerrorを判定していない。
- ユーザーは再読込時に以前の正常な一覧を空配列へ置き換える経路もある。
- 修正方針: 呼出元でerrorを判定するかthrowOnErrorを指定し、正常な0件と取得失敗を分離する。
- 根拠: Frontendの`Master/Users/List/service.tsx:66`、`Master/Services/List/service.tsx:115`、
  `Master/Machine/List/service.tsx:50`。各パスの接頭辞は`src/pages/`。
  生成クライアントの`src/generated/client/client.gen.ts:210`も照合した。

### PG-02: 通知の段階取得中に新着が入ると重複・欠落する

- 区分: 要修正。優先度: 高。
- 125件を新しい順で100件取得し、その後に新着1件を先頭へ追加すると、offset=100の取得位置がずれる。
- 模擬APIで取得行126件・ユニーク125件となり、既存の1件が重複、新着1件が取得されなかった。
- 画面は配列長の検索結果126件を表示するため、ユニークな通知総件数としては正しくない。
- 修正方針: 固定した取得境界またはカーソル方式を検討する。ID重複排除だけでは欠落は解消しない。
- 根拠: Frontendの`src/pages/Notifications/service.tsx:166`、
  Backendの`common/repository/NotificationRepository.java:460`。
  Backendパスの接頭辞は`src/main/java/jp/xoki/web/zunda/smarthomewebserverbackend/`。
- 検証境界: 実PostgreSQLへの同時書込ではなく、応答間にデータを増やす模擬APIで再現した。

### PG-03: サーバーページングで件数減少後に空ページが残る

- 区分: 要修正。優先度: 中。
- APIログ125件の7ページ目から5件へ減少させて再読込すると、offset=120のままとなる。
- 画面は0-0件・検索結果5件を表示し、前へは有効なまま。データがあるのに一覧が空に見える。
- クライアント方式の共通フックには縮小補正があるが、サーバー方式には同じ補正がない。
- 修正方針: total_countと現在のoffsetから範囲外を検出し、先頭または最終有効ページへ再取得する。
- 根拠: Frontendの`src/pages/Logs/View/page.tsx:37`。
  実行ログモーダルも同構造であり、保持期間等による減少時の確認対象とする。
  モーダルの減少ケース自体は今回未実行。

### PG-04: 検索条件変更後のページ位置が方式によって異なる

- 区分: 挙動統一候補。優先度: 中。
- ユーザー一覧2ページ目で125件から80件へ検索すると、21-40件のまま先頭へ戻らない。
- 共通フックは件数変更と範囲外補正のみを行うため、同フックを使う10画面に共通する。
- APIログは検索適用時に先頭へ戻る。共通設計のAPI連携節はサーバー方式について記載しており、
  画面内検索も同じ扱いにするかを明文化する必要がある。
- 根拠: Frontendの`src/hooks/useListPagination.ts:5`、`src/pages/Master/Users/List/page.tsx:18`。

### PG-05: APIキー更新中のページングが有効

- 区分: 挙動統一候補。優先度: 中。
- 発行POSTの応答待機中、再読込は無効だが件数選択と次へは有効だった。
- 通知画面は取得中と更新中の両方をページング制御へ渡すが、APIキー画面はloadingだけを渡している。
- 修正候補: 更新中も操作を固定する方針ならbusyをページングへ反映する。
  現行の共通設計は取得中のみを規定しているため、全画面の更新禁止を確定済み仕様とは扱わない。
- 根拠: Frontendの`src/pages/Master/ApiKeys/page.tsx:132`と同155行。

### PG-06: カレンダーの総件数は表示期間内のカード数ではない

- 区分: 仕様確認。優先度: 中。
- 全定義を検索・ページ分割してから、各日付に該当する定義だけをカード表示する。
- 表示期間外の定義2件で検索結果2件・表示カード0件を確認した。
- 毎日実行する125定義の週次表示では、20・50・100・最終25定義に対してカード数は140・350・700・175だった。
- 検索結果を定義数とするか表示期間内の該当定義数とするか、表示件数の単位と合わせて確認する。
  カードの繰り返し自体を不具合とは判定しない。
- 根拠: Frontendの`src/pages/Master/Batch/Schedule/List/page.tsx:101`と同340行。
