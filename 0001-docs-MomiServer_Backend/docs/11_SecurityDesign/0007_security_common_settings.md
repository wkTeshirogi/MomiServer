# セキュリティ共通設定・ログイン制御設計

## 概要

個人利用を前提に設定はファイルで管理し、管理者には有効な非機密値を参照専用で公開する。
ログインの失敗回数とロックは設定値と区別し、再起動で解除されないようDBへ保存する。
初期値と合意の経緯は[2026/10/26決定記録](../90_MeetingMinutesAndNotes/weekly_document_progress_20261026.md)を参照する。

## 対象範囲

| 区分 | 内容 |
| --- | --- |
| 対象 | Webログイン、JWT期限の参照、既存IoT制限の参照、外部在庫APIのキー単位上限 |
| 対象外 | Agent認証、画面からの設定保存、認証の全体停止、ロール変更によるロック |

## 認証

| 項目 | 方針 |
| --- | --- |
| 判定単位 | メールアドレスに一致する既存アカウント。ユーザー行ロックで認証・状態更新を直列化 |
| 許容回数 | 初期5回。6回目の試行は正しいパスワードでも照合前に拒否し、ロックを開始 |
| 解除 | 初期15分。ロック中の試行では解除予定時刻を延長しない |
| リセット | 成功時またはロック期限終了時に失敗回数を0へ戻す |
| 永続化 | `m_users.login_failure_count`と`login_locked_until`。V39で追加 |
| 失敗の確定 | 通常の認証失敗は状態更新をコミットしたうえで401を返す。DB障害まで成功扱いにはしない |
| 不明アカウント | 状態を新設せず、通常と同じ公開認証失敗応答にする |

既存のBAN_USER・セッション管理・パスワード変更との行ロック順序は維持する。
既に発行したJWTの期限を書き換える機能や、一時ロックに伴う既存セッションの一括失効は追加しない。

## 認可

| ロール | 許可操作 |
| --- | --- |
| ADMIN | 共通設定からセキュリティ設定を参照・再読込 |
| OPERATOR・USER・その他 | 設定APIと設定画面を利用不可 |

画面は`/master/common-settings/security`、APIは`GET /api/master/common-settings/security`。
応答項目はaccessTokenSeconds、refreshTokenSeconds、iotRateLimitEnabled、iotPerMinute、
externalInventoryHourlyLimit、loginFailureTolerance、loginLockMinutesだけとし、設定Bean全体を返さない。
編集・保存APIは提供しない。変更は`application.yaml`等の起動設定を修正して再起動する。

## 入力検証

| 対象 | 検証内容 |
| --- | --- |
| `app.security.login-failure-tolerance` | 1以上の整数。初期5 |
| `app.security.login-lock-minutes` | 1以上の整数。初期15 |
| `app.security.external-inventory-hourly-limit` | 1以上の整数。初期1,000 |

外部APIの消費処理とX-RateLimit応答は同じ設定値を使う。時間窓の更新・原子的な消費・キーごとのDB管理は維持する。
JWT期限とGateway制限には既存の設定キーを使用する。新しい設定保存用DBは作らない。

## エラーレスポンス

| 条件 | ステータス | 応答方針 |
| --- | --- | --- |
| パスワード不一致・ロック | 401 | 既存のAUTHENTICATION_FAILED。公開応答でロック状態や存在有無を区別しない |
| 設定の閲覧権限不足 | 403 | 既存の共通エラー |
| 未提供の保存操作 | 405 | メソッド不許可。サーバー障害として扱わない |
| 外部API上限到達 | 429 | 上限・残数・解除時刻のヘッダーを付与 |

## ログ・監査

ロック開始をコミットした後、別トランザクションでsecurity_alertを1回作成する。
現在のADMINのユーザーIDだけをブラウザ通知先に指定し、一般ユーザーへ配信しない。
全体のブラウザ・Discord有効設定と既存の保持期間に従う。ロック継続中には再通知しない。
通知本文はユーザーIDと解除予定時刻だけを含み、パスワード・JWT・APIキー原文は含めない。
通知失敗はログに残すが、コミット済みのロックを取り消さず、認証拒否を通知の成否に依存させない。

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 再起動でロックを迂回 | 実行状態をDBへ保存 |
| 並行試行による回数取り違え | 既存ユーザー行のロック下で判定・更新 |
| 存在確認や秘密値の露出 | 公開失敗応答を統一し、参照DTOを非機密項目に限定 |
| 攻撃による第三者アカウントのロック | 時限ロックと管理者通知。IP単位の追加防御は今回の範囲外 |
