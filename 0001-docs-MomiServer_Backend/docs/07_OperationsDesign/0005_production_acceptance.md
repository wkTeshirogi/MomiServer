# 本番導入・運用条件と受入確認

## 概要

2026/10/27のユーザー合意に基づき、個人利用を前提とした初期導入条件を定義する。
仕様の合意と、設定反映・実機での受入確認の完了は区別する。
本書の作成時点では、本番設定、バックアップ、監視、証明書更新等の構築・検証は行っていない。

MomiServerは現在開発中であり、本番への導入・運用はまだ開始していない。
現在の開発端末での起動・検証を本番運用とは扱わない。
完成後に予定先のCentOSサーバーへ導入し、受入確認を経て運用を開始する。
以下は導入後に適用する運用条件であり、既存のCentOS・Dockerがあることを導入済みの根拠としない。

既存の[起動・停止](0001_start_stop.md)、[設定管理](0002_configuration_management.md)、
[DB移行](0003_database_migration.md)、[Agent・MQTT運用](0004_agent_batch_runtime.md)を参照し、
本書には本番で合意した条件と完了判定を集約する。

## Web限定公開・検索非掲載

2026/10/29に、従来の外部接続VPN必須から、Web画面のみVPNなしで利用できる方針へ変更した。
必要な通信を用途別に限定し、同じHTTPS入口にあることを理由に全API・Gitを公開しない。

| 対象 | VPNなし外部公開 | 保護 |
| --- | --- | --- |
| Web画面・必要な静的資産 | 対象 | HTTPS。ログイン前画面を除く業務データは認証・認可必須 |
| Web画面の表示・操作に必要なAPI | 対象 | 認証処理の受付等を除き既存JWT・ロール・データ範囲を検証 |
| Web画面のリアルタイム更新 | 必要なWebSocketだけ対象 | 既存のチャネル別認可・接続チケットを維持 |
| Git Smart HTTP | 対象外 | clone・fetch・pull・pushはLAN／VPN内。PATが有効でも外部公開経路では拒否 |
| Agent端末向け・外部連携専用API | 対象外 | Web操作用APIと分離し、既存の専用認証も維持 |
| DB・MQTT・内部管理エンドポイント | 対象外 | 既存のネットワーク制限を維持 |

Webから使うrepo管理・履歴表示等の管理APIと、Gitプロトコルの通信受付は別に扱う。
Web公開によって既存ロールを緩和せず、通常ユーザーを管理者にする例外も設けない。
公開するAPI・WebSocketの具体的な許可一覧は詳細設計で定義し、全/api/**の一括公開は行わない。
公開入口でGitを拒否し、BEへの直接接続や未信頼の転送ヘッダーを利用した迂回も防ぐ。

### 検索非掲載とアクセス制御

- 公開サイトの応答にはログイン画面を含めて`X-Robots-Tag: noindex`を付与する設計とする。
- noindexを認証の代用にしない。API・添付・Gitの直接URLにも独立した認証・認可を適用する。
- robots.txtの全面遮断だけには頼らず、公開ページのnoindexを検索エンジンが取得できる構成にする。
- noindexを読ませる目的で、非公開API・データ・Gitのアクセス制限を解除しない。
- 公開前に既存の認証・認可、ログイン試行制限、脆弱性対応、公開経路の拒否を受入確認する。

[Google公式のnoindex仕様](https://developers.google.com/search/docs/crawling-indexing/block-indexing)に基づく対策とし、
すべてのクローラーの遵守や、第三者サイトでの言及まで抑止できる保証とは扱わない。
Let’s Encrypt証明書は[公開CTログ](https://letsencrypt.org/docs/ct-logs/)に登録されるため、ホスト名の存在秘匿とも区別する。
DNS名・検証方式・公開API一覧の決定と、Nginx・FW・ヘッダーの実装・検証は今後行う。本書で外部公開を設定したものではない。

| CA・証明書管理 | 提示されたCertbot更新設定はLet’s Encrypt本番接続、認証・反映ともnginx。計画ホスト名への適用は未決定 |

| 用途 | 正式配置 |
| --- | --- |
| BE配布物 | /opt/smarthome/ |

Git本体と作業領域は同一FSに置く。バックアップはWeb公開領域から分離し、web_appが書き換えられない権限とする。
/opt未マウント時は起動・取得を拒否する。既存データの移動やディレクトリ・権限の設定を実施した記録ではない。
同じ/opt上の別ディレクトリへの保存であり、ディスク故障への保護とは扱わない。外部退避先は引き続き準備する。
Gitの容量・転送・同時実行・時間制限の正本は[ストレージ設計](../02_SystemDesign/Git基盤/0001_storage.md)とする。
DB・Docker等が使う/varの容量監視も維持し、Gitを/optへ配置することと混同しない。

## バックアップ運用

### ソースコードのGitHub保管

ソースコードは今後GitHubにも保管し、サーバー外のバックアップを兼ねる予定とする。
GitHub側への保管・同期は未確認であり、今回の文書更新でリモート変更やpushは行わない。

- GitHubへ反映したソースコード・Git履歴と、DB・添付・実行環境の復旧資産は区別する。
- 未コミット変更やGitHubへ未送信のコミットが、GitHub上にも保管されているとは扱わない。
- DB、バッチ添付、MQTT設定、Agent状態、秘密情報はGitHub保管だけでは復旧できない。
- 秘密情報・認証情報・実データをソースバックアップのためにGitへ追加しない。
- 対象リポジトリ、公開範囲、同期方式・頻度、LFS等の追加資産の範囲は別途具体化する。
- 運用データの週次・月次取得とGitHubへのソース同期は別処理とし、頻度・保持も分けて管理する。

[Git基盤・GitHub連携の既存方針](../90_MeetingMinutesAndNotes/git_platform_and_notification_decisions_20261017.md)
は維持する。今回のソース保管予定を、将来のGitHub自動連携基盤の実装完了とは扱わない。
ソースの外部保管先ができても、NAS／外付けディスクによる運用データの外部退避は継続課題とする。

### 取得・保持・失敗時の扱い

| 項目 | 合意内容 |
| --- | --- |
| 週次取得 | 専用スクリプトで毎週月曜日03:00に差分バックアップを開始 |
| 月次取得 | 専用スクリプトで毎月1日03:00にフルバックアップを開始 |
| 日時・重複 | 日本時間。1日が月曜日なら週次差分を中止し、月次フルのみ実行 |
| 暫定保存先 | 同一サーバー内の/opt/smarthome-backups/ |
| 世代保持 | 正常な月次フル3世代・週次差分8世代。差分が依存するフルは世代上限を超えても保持 |
| 取得失敗 | 管理者へ通知し、既存の正常なバックアップは削除しない |
| 容量不足 | バックアップ失敗として通知。容量確保のために業務データを自動削除しない |
| 更新前 | 定期取得とは別に取得し、更新後の動作確認完了後も7日間保持する |
| 復元確認 | 初期導入時、バックアップ方式変更時、DBメジャーバージョン変更時 |
| 将来の保存先 | NASまたは外付けディスクへ退避し、その保存先からの復元も確認する |

追加合意により、従来の毎日01:00・成功14世代・最大1日分の損失という条件を上記へ置き換える。
2026/10/29に、週次差分は直近月次フルを比較元とし、DBは週次も完全アーカイブを取得する方式を合意した。
Git領域の取得・差分復元・整合点は[Gitバックアップ基本設計](../02_SystemDesign/Git基盤/0003_backup_restore.md)を参照する。
取得日時・月次優先・保持世代・更新前の別取得の保持期間は合意済み。
BE停止は30分以内を目標とし、時間超過は通知するが時間だけで強制終了しない。
一時失敗は終了から60分後に最大2回再試行し、容量不足・破損・設定不正は手動対応とする。
停止中の未開始予定は復帰後に1回補完し、期限到来した月次未成功ならフルを優先する。
詳細な再開・再試行・未取得補完の正本はGitバックアップ基本設計とし、他機能のファイルとの対応と実装・実証は残件とする。
Git repoの保守は当面、作業状況の状態管理までとするが、取得時の排他・書込停止・整合性確保は維持する。
新しい取得が成功してから世代整理を行い、失敗した取得物を正常世代として数えない。
保持する差分が依存するフル等を先に削除せず、復元に必要な組を維持する。
対象データ・ファイルを整合した状態で取得し、復元可能な組として管理する。
取得に失敗した場合は、最後に成功した時点以降の損失が1週間を超える可能性もある。

### 対象と保護

- DB、バッチ添付、MQTT設定、復旧に必要な設定・秘密情報を対象とする。
- Agentの状態・実行記録は各端末も対象とし、一般の一時ファイルとして削除しない。
- バックアップの保存先はアクセス制限を設ける。秘密情報・原文キーをGitやログに残さない。
- 一時保管する車検証原本の永続保管を目的としない。原本の既存削除契約を維持する。
- 取得方式、暗号化方法、秘密情報の復旧方法、各端末の収集方法、保存パスは実装前に具体化する。

### 暫定運用のリスク受容

外部保存先は未準備のため、同一サーバー内バックアップを暫定措置として初期導入を認める。
誤操作・更新失敗等への備えであり、サーバーや保存ディスク自体の故障には対応できない。
その場合はバックアップも失われる可能性があり、前述のデータ損失・復旧目標を保証できない。
外部退避未整備という制約を明記したうえで利用開始し、NAS／外付けディスク導入を継続管理する。

## データの保持・削除

| 対象 | 合意内容 |
| --- | --- |
| ログ・通知 | 過去1年分を保存し、それ以前を定期削除 |
| 一般的な一時ファイル | 生成から24時間経過後、定期清掃で削除 |
| 車検証原本 | 登録完了・取消・解析失敗時に削除。確認待ちは24時間で期限切れ |
| 処理中ファイル | 経過時間だけでは削除せず、処理終了を確認する |
| Agentの未送信結果・重複実行防止記録 | 一般の一時清掃から除外。未送信結果は保存日数・再送回数で打ち切らず受理まで保持。10月31日に上限撤廃を実装。本番受入は別途 |
| バックアップ | 一時清掃から除外し、バックアップの世代管理に従う |

アプリケーションのスケジューラーで毎日、期限に達した対象を確認し削除する。
日々の変更を追う場合も、当日追加分だけに限定せず、停止期間中や前回失敗時の削除漏れを回収する。
一時ファイルの保持は当初の2週間案を採用せず、最終回答の24時間に置き換える。
削除は期限到達後の定期清掃で行うため、24時間ちょうどでの物理削除を保証するものではない。
アプリケーション所有の専用領域を対象とし、OSや他サービスの一時領域を一律に削除しない。
OCR中間ファイル等の既存の早期削除を、24時間の保管へ延長する意味ではない。

「ログ・通知」はMomiServerが管理するデータを対象とする。
Discord投稿やGitLab等の他サービスの履歴の削除を、この合意だけで自動化しない。
アプリログ、APIログ、監査ログ、バッチ実行ログ、通知について実データとの対象対応を整理する。
1年を暦年差で扱うか365日で扱うか、削除基準の日時、清掃時刻、容量対策は実装前に確定する。
通知重複防止や実行制御の記録を、表示用の通知・ログと同じ期限で無条件に削除しない。

## 自動起動・停止・更新・復旧

### 導入版の識別

FE・BE・Agentを分けて追跡できるよう、各成果物と元のcommit SHAを対応付ける。
導入した構成要素の版・成果物識別子・導入日時・導入先を記録し、更新前後の組み合わせを確認できるようにする。
DBの適用済みマイグレーションも照合し、ソースの版だけで復旧可能と判断しない。
識別情報の保存先と表示・参照方法は未確定であり、版管理機能を実装済みとは扱わない。

### 更新・DB移行

| 操作 | 合意内容 |
| --- | --- |
| 自動起動 | 原則systemdで管理し、OS再起動後にDocker上の対象サービスを含めて復帰させる |
| 停止・更新 | MomiServer上のCI/CD実装までは手動。実装後に自動化する |
| 更新前確認 | バックアップを取得し、対象リリースのDB移行を検証環境で確認する |
| 実行中バッチ | 新規開始受付・自動配信を一時停止し、既存の実行が完了するまで待つ。更新の都合で強制停止しない |
| 未送信の結果 | 保存日数・再送回数の上限を設けず、サーバーの保存受理まで保持・再送する。バッチ本体を再実行しない |
| DB移行失敗 | 移行直前のバックアップから復旧する。失敗したまま運用開始せず、DBとアプリ版の整合を確認 |
| 更新後確認 | 起動、認証、主要機能、DB・MQTT・Agent接続、通知を確認する |
| 復旧 | 詳細な復旧手順の整備は後続対応。ただし初期導入時の検証用DBへの復元確認は必須 |

新規開始・自動配信の停止は合意済み。完了待ち中は結果受信の経路を維持し、完了と送信受理を区別する。
直前バックアップ取得後の業務書込み停止範囲と、バッチ完了待ちからDB移行までの保守モードは具体化が必要。
未送信結果は永続領域へ保存し、通信失敗・プロセス再起動・一時清掃を理由に失わない設計とする。
2026/10/28の追加合意では、Agentの未送信結果の保存日数・再送回数の上限を設けない方針を確定した。
計画更新時に限らず、サーバーの保存受理を確認するまで、日数・回数の超過を理由に破棄・再送打切りをしない。
一般の一時ファイルの24時間、サーバー側のログ・通知の1年という保持期限とは別に扱う。
Agent再起動後も未送信状態を復元し、同じ実行IDの結果を再送する。結果再送のために処理本体を再実行しない。
回数・日数の上限撤廃は、通信の連続即時再送や、1回のHTTP待機・バッチ実行時間の無制限化を意味しない。
再送間隔、通信タイムアウト、認証失効等の恒久エラー、容量不足時の保全・通知方法は別途具体化する。
受理済み結果の本文回収と、二重実行を防ぐID記録の保持は、未送信結果の上限撤廃とは分けて設計する。
10月31日にAgentの上限撤廃・受理照合・未受理時の起動抑制と、BEの保守APIを実装した。
具体的な更新順・停止条件・保存領域は[常駐・保守運用](0004_agent_batch_runtime.md)を正とする。
容量警告の外部通知、長時間停止、保存媒体障害、実機の更新・バックアップ一連の受入は残る。

実際の障害発生時の切り分け、復旧順序、切戻し、GitHubからのソース取得・再構築の手順は今後検討する。
ソースの保管予定を、システム全体の復旧手順が確立したことや復旧目標達成の証跡とは扱わない。
DBを復元する場合は、Agent側の保存結果・実行済み記録との整合も確認する。
停止・復帰時は実行中バッチとAgentの記録を照合し、成否不明を理由に自動再実行しない。
BE・Gitはweb_appを使用する。起動順序、バックアップ側の実行アカウント、再起動条件、手動更新手順は未確定。
CI/CD完成後の自動化を、現時点で実装済みとは扱わない。

### 管理者の緊急復旧

通常利用する管理者とは別に緊急用の管理手段を用意し、通常は利用不可とする方針を合意した。
DBを直接操作できる管理者が必要時に状態を変更し、通常の管理者権限・利用状態を復旧する。
別ロールは追加せず、通常は無効な専用の緊急ADMINアカウントを用意し、DB操作で一時的に有効化する。
通常の管理者復旧後は緊急アカウントを再び無効化する。通常の認証・認可を通し、認証迂回APIは追加しない。
操作権限、認証情報の保管、ロック状態の扱い、利用記録、再無効化時のセッション処理は設計時に具体化する。
既存の管理者ロック・認証処理は、この方針の合意だけでは変更しない。

### 停止期間をまたぐ通知・データ

停止中の通知も必要とし、復帰後にサーバーへ保存する方針を合意した。
Agent側で発生した通知・結果と、車検期限等のサーバー側で未判定の通知の両方を対象とする。
Agent側は未送信データを保持し、サーバー側は停止期間を考慮して復帰時に判定・保存する。
発生日時と受信・保存日時、保存先、復帰時の再送・重複防止方式は具体化が必要。
サーバー側の遡及期間・通知段階の選択・業務データ更新との整合も別途確定する。
この追加要件によって、予定時刻を過ぎたバッチを実行しない既存方針は変更しない。
サーバー未到達データの保存・再送と、Discordへの送信失敗時に再送しない方針も区別する。

## TLS・秘密情報管理

- LAN／VPN内でもHTTPS・MQTTのTLSを基本とし、証明書検証を無効化しない。
- 証明書は自動更新し、利用サービスへの反映まで行う。
- Web外部公開用の具体的DNS名は選定待ちとする。旧計画名momi.zundamochi.localと既存公開CAの不整合は未解消とする。
- 発行・更新クライアントは既存のCertbotを使用する。Certbot自体を発行元CAと扱わない。
- 提示された更新設定の接続先・プラグインは下表のとおり。更新の定期実行・実際の証明書内容・反映動作は未検証とする。
- 確認では接続先・認証方式等の非秘密情報に限定し、秘密鍵やDNS APIトークンを記録・共有しない。
- [Certbot公式ガイド](https://eff-certbot.readthedocs.io/en/stable/using.html)の取得・更新・ACME接続先の設定を参照する。
- 秘密情報も自動交換を目標とするが、資格情報ごとに連携先切替・旧鍵併用・再暗号化等を設計する。
- JWT署名鍵、DB資格情報、Agent暗号化鍵、Discord Webhook等を単純に一括上書きしない。
- 特にAgent暗号化鍵は保存済みデータの復号に関わるため、交換手順の実装前は自動変更しない。
- 開発用の秘密値・公開設定をそのまま本番へ流用しない。

### 提示されたCertbot更新設定と確認事項

2026/10/29にユーザーがサーバー上で抽出した設定値を受領した。こちらからサーバーへ接続して取得したものではない。

| 項目 | 提示された値 |
| --- | --- |
| 更新設定ファイル | /etc/letsencrypt/renewal/zundamon.f5.si.conf |
| server | `https://acme-v02.api.letsencrypt.org/directory` |
| authenticator | nginx |
| installer | nginx |

接続先はLet’s Encrypt本番環境と判断できる。ファイル名だけで証明書のSAN・有効期限や管理可能なDNS範囲を推測しない。
この1件の設定から、別途プライベートCAが存在するかどうかも断定しない。

- 公開信頼TLS証明書には内部名を含められないため、Let’s Encryptをmomi.zundamochi.localへ適用することはできない。
  根拠は[CA/Browser Forumの内部名制限](https://cabforum.org/working-groups/server/baseline-requirements/documents/BRv2.0.3.pdf)とする。
- Certbotのnginx認証はHTTP-01方式であり、公開CAから検証用HTTPへの到達が必要となる。
- 管理可能な公開DNS名とDNS-01検証を使用する案は、DNS更新権限と自動化可否の確認が必要とする。
  Web限定公開は合意済みだが、DNS-01への変更や証明書検証用ポートの追加公開を決定したものではない。
- .localを維持する場合は、その名前を発行できるプライベートCAと端末への信頼配布が必要となる。
- 証明書検証・CA方式は未採用の選択肢であり、具体的なホスト名変更、CA追加、ポート公開、更新設定変更は別途判断する。

HTTP-01・DNS-01の成立条件は[Let’s Encrypt公式の検証方式](https://letsencrypt.org/docs/challenge-types/)を参照する。
Certbotの更新タイマー、更新後のNginx反映、MomiServerの最終ホスト名・CA方式・クライアント信頼は引き続き確認する。

## 障害監視・通知

| 項目 | 合意内容 |
| --- | --- |
| 監視端末 | Raspberry Pi |
| Raspberry Piの監視対象 | サーバー稼働状況（到達性・Web応答）と証明書期限 |
| 容量管理 | ディスク管理はMomiServer側で行う。Raspberry Pi側の監視対象には含めない |
| バックアップ管理 | 専用スクリプトで取得・結果管理を行い、Raspberry Pi側の監視対象から分離する |
| 監視周期 | 1分ごと |
| 障害判定 | 同一監視項目で3回連続異常となった場合 |
| 障害通知 | Discordへ障害発生につき1回。継続中に毎分通知しない |
| 復旧通知 | 異常状態から復旧した場合にDiscordへ1回 |

監視状態の保存方法、証明書期限の閾値、監視先URL、スクリプト側の成功・失敗記録は未確定。
MomiServer側の容量管理の閾値・動作も別途具体化する。
MomiServerが停止している場合は、同アプリ内の容量管理・通知も利用できない制約を明記する。
主サーバー停止時も検知・通知できる構成とし、主サーバー上の通知処理だけに依存しない。
Raspberry Pi自体・ネットワーク・Discordが停止した場合は通知できない制約を了承する。
既存方針の「配信先設定後の再通知不要」「Discord送信失敗時の再送不要」は維持する。
