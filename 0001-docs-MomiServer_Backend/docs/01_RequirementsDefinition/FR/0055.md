# Git操作受付

| 項目 | 内容 |
| --- | --- |
| 機能ID | FR-0055 |
| カテゴリ | Gitサーバ |
| 優先度 | 高 |
| 初期実装フェーズ | Git基盤 Phase 1 |

## 概要

標準GitクライアントからGit Smart HTTPを使用したclone、fetch、pullおよびpushを受け付け、
Personal Access Token、リポジトリ権限およびref保護規則に基づいて操作を制御する。

初期アクセス方式はHTTPSに限定する。SSHアクセスは現在の利用要件に含めず、当面の実装予定を持たない将来検討機能とする。

## 前提

- 外部からのGit通信はTLSで保護されたHTTPSを使用する。
- Git通信はLAN／VPN内に限定する。VPNなしの外部公開はWeb画面と必要なAPI・WebSocketのみとする。
- 同じHTTPS入口でもGit Smart HTTPは公開経路で拒否し、有効なPATを外部公開の許可条件にしない。
- リバースプロキシでTLSを終端する場合も、信頼するプロキシと転送ヘッダーを限定し、外部URLがHTTPSであることを保証する。
- Gitプロトコルを独自実装せず、JGitのSmart HTTP機能を採用候補とする。
- JGitの正式採用は、MomiServerで使用するSpring BootおよびServletコンテナとの互換性検証後に決定する。

## 機能要件

### Git Smart HTTP

- `git-upload-pack`を使用するclone、fetchおよびpullを受け付けること。
- `git-receive-pack`を使用するpushを受け付けること。
- URL上のグループおよびリポジトリを、FR-0054で管理する内部IDへ安全に解決すること。
- 存在しない、無効または削除待ちのリポジトリに対して、定義したエラー応答を返すこと。
- セッションCookieに依存せず、各Git HTTP要求を認証・認可すること。

### 認証

- HTTPSのHTTP Basic認証を利用し、パスワード部分へPersonal Access Tokenを指定できること。
- PATの平文は発行時の一度だけ表示し、サーバーには復元できないハッシュとして保存すること。
- PATごとに名称、所有者、スコープ、有効期限、発行日時、最終利用日時、失効日時および状態を管理すること。
- PATを即時に失効でき、失効後の要求を拒否できること。
- PATの照合はタイミング差を利用した推測を困難にする方式で行うこと。
- 認証失敗の連続試行を制限し、試行元、対象および結果を監査対象とすること。

### 認可

- 最低限`read`、`write`および`admin`のリポジトリ権限を定義すること。
- clone、fetchおよびpullには`read`、pushには`write`以上を要求すること。
- リポジトリ設定、権限設定、論理削除および復元には`admin`を要求すること。
- システム、グループおよびリポジトリ単位の権限を解決する優先順位を一意に定義すること。
- 初期実装ではbranch単位の読み取り権限を設けず、リポジトリを読める利用者は全refを取得できるものとすること。
- 未認証と認証済み権限不足を区別し、HTTPおよびGitクライアントで判別可能な応答を返すこと。

### ref保護

- pre-receive相当の処理で、refを更新する前に全更新内容を検証すること。
- 保護対象branchへの直接push、non-fast-forward更新、branch削除およびtag上書きの可否を設定できること。
- `main`は既定で保護対象とし、許可されていない直接push、force pushおよび削除を拒否すること。
- 複数refを含むpushでは、一部だけを更新して監査上不明確な状態を作らないよう、原子的更新の対応可否を検証し、非対応時の動作を明示すること。
- 拒否理由をGitクライアントへ返し、監査記録へ残すこと。ただしSecretや内部物理パスを含めないこと。

### 操作完了イベント

- push完了後、成功したref更新ごとにリポジトリ内部ID、実行者、ref名、更新前後のobject ID、結果および日時を記録すること。
- 操作完了イベントは、リポジトリ内部ID、ref名、更新前後のobject IDおよび操作種別から重複判定できること。
- Git更新成功後にデータベース保存が失敗してもGit更新を巻き戻そうとせず、再試行または照合処理で監査記録を補完すること。
- Gitイベントを後続のCI/CDおよび通知が利用できる形式で発行すること。ただし、本要件ではCI/CD実行やDiscord送信を行わないこと。

## 非機能要件

- 無通信タイムアウト、操作全体の上限時間、単一オブジェクトサイズおよびpush単位のpackサイズを設定できること。
- リポジトリ上限またはサーバーの空き容量下限を超えるpushを、可能な限りref更新前に拒否すること。
- 同時push、通信中断、クライアントの再送および不正なpackを受信しても、既存refと到達可能なGitオブジェクトを破損しないこと。
- 認証情報、PAT、AuthorizationヘッダーおよびGitオブジェクトの内容を通常のアクセスログへ出力しないこと。
- Git操作のエラー応答へスタックトレース、物理パスまたは内部実装情報を含めないこと。

## 初期対象外

- SSHによるclone、fetch、pullおよびpush
- SSH公開鍵の登録・失効・ローテーション
- Git LFSプロトコル
- partial cloneおよびpromisor remote
- SHA-256オブジェクト形式
- コミット署名およびタグ署名の検証・強制
- 任意のサーバーサイドシェルhook
- branch単位の読み取り権限

SSHアクセスは、HTTPS運用で解決できない要件が発生した場合に独立した要件として再評価し、Phase 1の完了条件には含めない。

## 受入条件

- 標準Gitクライアントから有効なPATを使用してclone、fetch、pullおよびpushを実行できること。
- PAT未指定、無効、期限切れまたは失効済みの場合に操作が拒否されること。
- `read`権限のみの利用者によるpushと、権限を持たない利用者による取得が拒否されること。
- 保護された`main`へのforce push、削除および許可されていない直接pushがref更新前に拒否されること。
- 同時pushおよび通信中断後に整合性検査を行い、既存の到達可能なcommitとrefが破損していないこと。
- 成功したpushのref更新と実行者を監査記録から追跡できること。
