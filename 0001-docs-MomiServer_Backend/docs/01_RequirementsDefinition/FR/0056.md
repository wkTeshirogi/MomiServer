# Git基盤状態・監査・復旧管理

| 項目 | 内容 |
| --- | --- |
| 機能ID | FR-0056 |
| カテゴリ | Gitサーバ |
| 優先度 | 高 |
| 初期実装フェーズ | Git基盤 Phase 1 |

## 概要

MomiServer内蔵Git基盤の稼働状態、容量、操作結果、監査イベント、バックアップおよび復旧状態を管理する。

Git ref更新の確定はイベント駆動で反映し、定期監視はヘルスチェック、容量確認および不整合検出の補完に限定する。
CI/CD、GitHub連携およびGit専用通知はGit基盤とは別の機能境界として管理する。

## 機能要件

### 稼働状態・容量

- Gitサービス全体とリポジトリごとに、利用可能、読み取り専用、無効、容量不足、異常、復旧中の状態を管理できること。
- 保存領域の総容量、使用量、空き容量、空き容量下限および最終確認日時を取得できること。
- リポジトリごとの使用容量、最終アクセス日時、最終push日時および最終整合性確認日時を参照できること。
- 容量不足または整合性異常を検出した場合、新規pushを停止し、取得操作を継続できるかを状態と障害内容に基づいて決定すること。

### 操作・監査履歴

- リポジトリの作成、設定変更、権限変更、無効化、論理削除、復元および物理削除を監査対象とすること。
- clone、fetch、pushの認証結果、認可結果、対象リポジトリ、実行者、日時、結果およびエラー分類を記録できること。
- push成功時に、更新対象ref、更新前後のobject IDおよび保護規則の判定結果を追跡できること。
- PATの発行、失効、期限切れおよび不正利用試行を監査対象とすること。
- 監査記録にPAT、Authorizationヘッダー、SecretまたはGitオブジェクトの内容を保存しないこと。
- 監査記録の保持期間と削除手順を設定できること。

### Gitとデータベースの整合性

- Gitファイルシステムのref更新とデータベース上の監査・イベント記録を、異なる永続化境界として扱うこと。
- Git更新後のイベント保存に失敗した場合、冪等な再試行またはref照合によって記録を補完できること。
- 起動時および定期実行時に、登録済みリポジトリの存在、HEAD、ref、管理状態および保存先の対応を照合できること。
- データベースだけ、またはファイルシステムだけに存在するリポジトリを異常として検出し、自動削除しないこと。
- 不整合の自動修復範囲と管理者確認が必要な範囲を分離すること。

### バックアップ・復旧

- バックアップごとに、リポジトリ内部ID、取得日時、全対象refとcommit SHA、Gitオブジェクト形式および対応する管理情報の版をマニフェストとして記録すること。
- Gitリポジトリとデータベース上の管理情報について、整合した復旧点を識別できること。
- バックアップの成功、失敗、検証結果、保存先および保持期限を管理できること。
- 本番領域を上書きせず、別領域へ復元してrefとcommit SHAを検証できること。
- 復元完了前は対象リポジトリへの書き込みを許可しないこと。
- GitHubへのバックアップまたは公開ミラーは補助的な複製として扱い、MomiServerのバックアップ・復旧要件を代替しないこと。

### 保守

- 初期のrepo保守は最終作業日時からの利用状況の状態管理に限定すること。期間nの初期値は90日とする。
- 成功したpushおよびrepo設定変更を作業対象とし、clone・fetch・監視・バックアップ・失敗操作は含めないこと。
- 利用状況をlifecycle・healthと分離し、長期間利用がないだけで自動停止・削除・アーカイブを行わないこと。
- Gitの制限値と作業判定期間をADMIN向け共通設定で変更可能とし、変更履歴と入力検証を設けること。
- GC、repackおよびpruneの実行機能は将来対応とし、初期実装の自動清掃対象に含めないこと。
- 将来の清掃ではpush・バックアップ・復元との排他、復旧猶予、バックアップおよび監査を必須とすること。

猶予日数・利用状況・保持条件の正本は[Git基盤基本設計](../../02_SystemDesign/Git基盤/000_index.md)とする。
この段階分けはrepo保守の実行範囲についてのものであり、既存のヘルスチェック・容量保護・監査補完や
バックアップ取得時の書込停止・整合性確保を省略する意味ではない。

## 非機能要件

- ref更新、認証・認可エラーおよびGit操作結果は、60秒間隔のポーリングではなく操作時に記録すること。
- ヘルスチェック、容量および不整合の定期確認間隔は設定可能とし、初期値は60秒とすること。
- 一時的な確認失敗と継続的な障害を区別し、設定した連続失敗回数を超えた場合に異常状態へ遷移すること。
- 監視処理自体の最終成功日時を保持し、監視停止を検出できること。

## 機能境界

### 後続の独立機能へ引き渡す情報

- CI/CD基盤には、リポジトリ内部ID、ref、更新前後のobject ID、実行者およびイベント日時を引き渡す。
- Git専用通知には、Git操作またはCI/CDの確定済みイベントIDと通知判断に必要な情報だけを引き渡す。
- GitHub連携には、同期対象リポジトリ、同期モードおよび確定済みref情報を引き渡す。

### 本要件で管理しない情報

- Pipeline、StageおよびJobの実行状態
- CI/CD実行ログ、テストレポート、成果物およびCache
- 定期的なDependency-Check、SonarQubeその他のチェック結果
- GitHub同期ジョブ、公開承認および同期先設定
- Discord Webhook、通知ルール、配信状態および再送状態
- Pull Request相当のマージ要求、レビュー、承認およびマージ完了状態

## 初期対象外

- 複数ノードのGitサービスを前提とする分散ロックおよび自動フェイルオーバー
- GitHubのみから復旧することを前提としたバックアップ
- 利用者定義スクリプトによる保守・監視処理
- CI/CDまたは通知の成否をGit操作の成功条件とする同期処理

## 受入条件

- push成功直後にref更新履歴を参照でき、定期監視を待つ必要がないこと。
- Git更新後のイベント保存失敗を再現し、再試行または照合によって監査記録を一度だけ補完できること。
- データベースとファイルシステムの片側だけに存在するリポジトリを検出し、自動削除しないこと。
- 容量下限超過時に新規pushを停止し、エラー理由を監査記録から確認できること。
- バックアップを別領域へ復元し、マニフェストに記録した全refのcommit SHAと一致すること。
- GitHub、DiscordまたはCI/CD実行基盤が停止していても、確定可能なGit操作を巻き戻さないこと。
