# リポジトリ管理

| 項目 | 内容 |
| --- | --- |
| 機能ID | FR-0054 |
| カテゴリ | Gitサーバ |
| 優先度 | 高 |
| 初期実装フェーズ | Git基盤 Phase 1 |

## 概要

MomiServerをGitリポジトリの正本として使用するため、サーバー内部にbare repositoryを作成し、
データベース上の管理情報と対応付けてライフサイクルを管理する。

Phase 0では本要件と対象外範囲を確定し、実装はJGitの技術検証完了後に開始する。

## 前提

- 初期構成は単一のMomiServer Backendからリポジトリへ書き込む単一ノード構成とする。
- リポジトリはMomiServerが管理するローカルかつ永続的なファイルシステムへ保存する。
- 初期対応するGitオブジェクト形式はSHA-1とする。
- リポジトリの表示名およびURL上のパスと、物理保存先を直接対応付けない。

## 機能要件

### リポジトリ作成

- 管理者または作成権限を持つ利用者が、所属グループ、リポジトリ名、説明および公開範囲を指定して作成できること。
- 作成時に変更しない内部IDを発行し、データベース上の管理情報とbare repositoryを内部IDで対応付けること。
- 空リポジトリの既定ブランチは`main`とし、HEADを`refs/heads/main`へ設定すること。
- 同一グループ内で正規化後のリポジトリ名が重複しないこと。
- 許可する文字、最大長、予約語および大文字・小文字の同一視規則を設定し、不正な名前を登録前に拒否すること。
- リポジトリ作成の途中でデータベースまたはファイルシステムの処理に失敗した場合、未完了状態を検出して再実行または安全な回収ができること。

### MomiServer内の管理画面

- 一覧、作成、詳細、権限設定を既存Frontendへ組み込み、管理API・認可は既存Backendへ配置すること。外部Gitサービスへのリンクで代替しないこと。
- 一覧は許可されたグループ・リポジトリだけを表示し、検索条件と認可を適用した総件数でページングすること。初期20件、20・50・100件を選択できること。
- 作成画面は所属グループ、名前、説明、既定branch等を入力し、内部ID・物理パス・既存設定を利用者入力から決定しないこと。
- 詳細画面は管理情報、ライフサイクル・健全性・利用状況、branch・tag・commit履歴、HTTPS Gitの接続先を確認できること。
- Web参照はWeb JWTとGit ACLで認可し、Git通信は専用PATで認証すること。公開Web画面からGit通信のLAN/VPN制限を迂回しないこと。
- readは閲覧、writeはGit書込み、adminは管理設定の操作とし、画面で非表示にするだけでなく各APIでも認可すること。システムADMINの全repo管理例外は認証認可基本設計に従うこと。
- 設定・権限変更の競合と失敗を通知し、利用者の未保存入力を保持すること。秘密値・物理パスをエラーへ露出しないこと。
- 作成時に主要言語、CI/CD利用、通常・定期チェックの選択を扱い、詳細な設定・継承・更新履歴は[CI/CD項目の判断記録](../../90_MeetingMinutesAndNotes/git_platform_and_notification_decisions_20261017.md)を参照すること。
- 未実装の実行・通知・公開連携を動作済みの操作として表示しないこと。任意コマンドをBackend上で実行する機能にしないこと。

2026/10/31に画面の必須操作と認可境界を要件へ反映した。URL・入力制約・CI設定保存・秘密情報継承等の詳細化と実装は後続とする。

### リポジトリ参照・更新

- リポジトリの名称、説明、所属グループ、既定ブランチ、状態、作成者、作成日時および更新日時を参照できること。
- ブランチ、タグおよびコミット履歴を参照できること。
- 表示名または所属グループを変更しても、内部IDおよび物理保存先を変更しないこと。
- リポジトリを有効、無効、削除待ち、復元中、異常の状態で管理できること。
- 無効または削除待ちのリポジトリに対するGitアクセスの可否を状態ごとに定義し、少なくともpushは拒否すること。

### 削除・復元

- リポジトリの削除操作は即時の物理削除ではなく論理削除とすること。
- 論理削除時に削除実行者、削除日時および削除理由を記録すること。
- 設定可能な猶予期間内は、同じ内部IDとGit履歴を保持したまま復元できること。
- 物理削除は、猶予期間の経過、必要なバックアップの取得および管理者による実行条件の確認後に行うこと。
- 物理削除後も、定められた監査保持期間中は削除操作の監査記録を保持すること。

### ストレージ保護

- URL、リポジトリ名または利用者入力を連結して物理パスを生成しないこと。
- パストラバーサル、シンボリックリンクまたはジャンクションを利用した管理領域外へのアクセスを拒否すること。
- Gitリポジトリ以外のファイルをGitクライアントへ公開しないこと。
- リポジトリごとの使用容量と最終確認日時を取得できること。

## 非機能要件

- Gitオブジェクト、全refおよびデータベース上の管理情報をバックアップ対象に含めること。
- ライブリポジトリを整合性保証なしにファイルコピーせず、停止、スナップショットまたはGitの参照整合性を保証できる方式を使用すること。
- 復元時に全対象refのcommit SHAをバックアップ時のマニフェストと照合できること。
- 保存先は、ファイルロック、同一ファイルシステム内の原子的なrenameおよびJGitの利用条件を満たすこと。
- ネットワークファイルシステムを使用する場合は、正式採用前にロック、rename、同時pushおよび障害復旧を個別に検証すること。

## 初期対象外

- SHA-256オブジェクト形式のリポジトリ
- Git LFSオブジェクトの保存・配信
- 複数ノードから同一bare repositoryへ書き込むactive-active構成
- GitHubを唯一のバックアップとして扱う運用
- リポジトリの即時物理削除
- 任意の利用者が指定したサーバーサイドスクリプトの実行

## 受入条件

- 作成した空リポジトリのHEADが`refs/heads/main`を指していること。
- リポジトリ名を変更しても内部IDとGit履歴を維持し、変更後のURLからアクセスできること。
- 論理削除したリポジトリを猶予期間内に復元し、削除前の全refとcommit SHAが一致すること。
- パストラバーサルおよび管理領域外のシンボリックリンク参照が拒否されること。
- バックアップを別領域へ復元し、全対象refのcommit SHAと管理情報を照合できること。
