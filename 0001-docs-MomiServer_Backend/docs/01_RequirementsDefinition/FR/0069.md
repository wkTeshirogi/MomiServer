# API統合管理

| 項目 | 内容 |
| --- | --- |
| 機能ID | FR-0069 |
| カテゴリ | API Gateway |
| 優先度 | 中 |

## 概要

全APIエンドポイントの定義・バージョン・ドキュメントを一元管理する機能。

Phase 1では、実装済み経路から生成するOpenAPIと、Agent・IoTのAPIバージョン公開状態を管理する。APIエンドポイント一覧をDBで二重管理しない。

## Phase 1の管理範囲

- 実装対象バージョンはAgent・IoTとも `v1` とする。DBに別バージョンを追加するだけでは公開しない。
- `m_api_versions` の `active`、`deprecated`、`retired` をリクエスト時に判定する。状態変更はマイグレーション等の運用変更で行い、管理画面・編集APIは設けない。
- OpenAPIは実装済みControllerから生成し、Web JWT、Agent専用Bearer、IoT APIキー、認証不要の操作を区別する。
- `GATEWAY_OPENAPI_PUBLIC_ENABLED=true` はOpenAPI/Swagger UIを公開し、`false` はADMIN権限を要求する。

## 機能要件

- OpenAPI（Swagger）仕様でAPIを定義・公開すること
- APIのバージョン付きパスに対応すること。Phase 1は `/api/v1/` のみを実装対象とする
- Agentや自作IoT機器など外部連携APIは、必ず `/api/v{バージョン番号}` で始まるパスにすること
- APIバージョンの有効状態、非推奨状態、廃止予定はDBで管理できること
- クライアントごとの利用可能APIバージョン管理は将来対応とする。既存の `m_external_clients` は現行Agent認証には使用しない
- 非推奨APIへのリクエスト時に `Deprecation` ヘッダーで日時を通知すること
- OpenAPI公開可否は `.env` で管理できること
- Gateway経由のアクセス履歴管理は現時点では未定とし、必須実装対象に含めないこと

## 非機能要件

- OpenAPIドキュメントは常に実装と同期して最新状態を保つこと

## Phase 1完了条件

| 確認項目 | 完了条件 |
| --- | --- |
| 経路 | 未実装版・DB未登録版は404、廃止版は410を返す。DB参照失敗時は判定を迂回せず503を返す |
| 非推奨 | 対象APIを継続利用でき、`Deprecation` に日時を示す構造化ヘッダーを返す |
| 認証 | バージョン判定後もAgent専用Bearer、IoT向けGateway設定、Web JWTの境界を維持する |
| OpenAPI | 公開設定の両状態を確認し、各操作の認証表示が実装と一致する |
| 検証 | 状態別・認証別・公開設定別の自動テストとドキュメントビルドが成功する |

クライアント別許可バージョン、管理画面・編集API、DBによるAPI経路一覧管理、Gatewayアクセス履歴はPhase 1の完了条件に含めない。複数版の同時提供を始める前に、Agent専用認証と整合するクライアント識別・許可モデルを再設計する。

検証方法と実行結果は[Gatewayテスト設計](../../08_TestDesign/0005_gateway_test.md)を参照する。
