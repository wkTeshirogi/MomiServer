# エージェント連携API追加案 2026/09/13

## サマリ

Phase1のエージェント登録、設定取得、端末情報送信、バッチ受付、再接続時の照合に必要なAPI候補を記録する。
本書は議事録・作業メモテンプレートを基にした検討案であり、実装済みAPI一覧や確定したAPI契約ではない。
登録・専用認証は2026年9月23日に実装した。[確定したAPI契約](API/0041_agent_registration_authentication.md)を参照する。
本書の監視報告・受付・同期などの残項目は引き続き追加案である。

## 決定事項

登録フローの合意は[エージェント事前登録・登録コード連携](../02_SystemDesign/認証/0004_agent_registration.md)を正とする。
登録コードの期限・利用回数・再試行・端末交換の条件は本書へ重複記載しない。
Agent連携に外部API向けAPIキーを使用せず、登録後はエージェント専用認証情報を用いる方針とする。

## 作業内容

### 追加API候補

| 用途 | メソッド・パス案 | 入力・処理の案 | 応答・用途の案 |
| --- | --- | --- | --- |
| 端末登録 | POST `/api/v1/agent/register` | 登録コード・登録要求ID・端末情報を受信し、事前登録情報へ紐付ける。 | エージェントID、専用認証情報、MQTTクライアントID、接続設定。 |
| 認証情報更新 | POST `/api/v1/agent/auth/refresh`（実装済み） | 登録済み端末が専用認証情報を更新する。 | 更新結果。期限・失効・再試行も合わせて設計する。 |
| 監視・実行環境設定取得 | GET `/api/v1/agent/settings` | 認証した端末に適用する設定を取得する。 | 監視間隔・閾値、OS別実行環境の初期値、設定バージョン。 |
| 端末情報・ハートビート送信 | POST `/api/v1/agent/reports` | 通常報告と軽量ハートビートを同じAPIで受信する。 | 保存・受理結果。 |
| バッチ受付通知 | POST `/api/v1/agent/batch/executions/{executionId}/accept` | エージェントが実行ID・要求をローカル保存した後に通知する。 | 受付の受理結果。 |
| 再接続時の照合 | POST `/api/v1/agent/batch/sync` | 実行IDごとに受付・実行・結果の状態を照合する。 | サーバ側の受理状況、キャンセル要求、未受信要求等。 |

管理画面向けには基本情報登録、登録コード発行・再発行、端末再登録の操作も必要になる。
既存のマスタ管理との関係を確認してAPI構成を決める。削除専用APIは設けず、無効化は状態更新で扱う。
登録コード発行は管理者権限、端末登録は登録コードと再試行確認、登録後の操作は専用認証で保護する。

### 既存APIを利用・拡張する範囲

以下は仕様検討時にバックエンドのControllerで存在を確認したAPIである。
存在確認は、認可・再送・照合が合意仕様をすべて満たすことの保証ではない。

| 用途 | メソッド・パス | 確認・拡張する点 |
| --- | --- | --- |
| バッチ共通設定取得 | GET `/api/v1/agent/batch/settings` | 合意済み設定と要求単位の設定への対応。新設settingsとの項目重複を避ける。 |
| 実行開始通知 | POST `/api/v1/agent/batch/executions/{executionId}/start` | 実際の開始日時保持、再送時の重複処理防止、対象エージェントの認可。 |
| 実行完了通知 | POST `/api/v1/agent/batch/executions/{executionId}/complete` | 実際の終了日時等の追加、停止・未開始確認、遅延結果の受理。 |
| 実行状態照会 | GET `/api/v1/agent/batch/executions/{executionId}/state` | 受理済み状態・キャンセル情報を照合に利用する。 |
| ファイル一覧取得 | GET `/api/v1/agent/batch/executions/{executionId}/files` | 対象エージェントの認可と配布情報の整合。 |
| ファイル取得 | GET `/api/v1/agent/batch/executions/{executionId}/files/{fileId}/download` | 対象実行に紐付くファイルの取得。 |

### 端末報告の構成案

| 情報 | 通常報告 | 高負荷継続中の軽量報告 |
| --- | --- | --- |
| エージェント識別・送信日時 | 含む。認証主体との整合を確認する。 | 含む。 |
| 高負荷・送信抑制状態 | 含む。 | 含む。 |
| 実行中バッチ数 | 含む。 | 含む。 |
| CPU・GPU・メモリ・ディスク詳細 | 取得日時・取得可否とともに含む。 | 省略する。 |
| 容量警告・回復の最新状態 | 含む。 | 含む。 |

詳細値の省略は削除指示として扱わず、バックエンドは前回の観測値と取得日時を保持する。
取得不可・項目省略・有効な0の区別と、古い報告で最新値を上書きしない判定方法をAPI契約で定義する。
再送中も観測値を更新するため、報告の識別子と重複受理の単位は別途確定する。
送信周期・負荷判定・ハートビートの数値はエージェント設計の
`docs/02_SystemDesign/Details/060_resource_monitoring.md`と`020_connection_management.md`を参照する。

### 受付と照合の構成案

MQTTへの配信成功とエージェントによる永続化済み受付を区別する。
受付通知では実行ステータスを増やさず、受付日時・確認状況で管理する案とする。
受理済みの開始・完了状態を、遅れて届いた受付通知で巻き戻さない。
syncはエージェントが既知のIDだけでなく、停止中に作成された未受信要求も発見できる契約とする。
開始期限・キャンセル・重複防止を確認し、再配信をバッチの再実行と混同しない。

### 共通契約案

- 認証したエージェント自身の設定・情報・実行要求だけを操作可能とする。本文のIDだけで権限を決めない。
- 開始・完了通知の同一内容の再送で、日時・履歴・結果を重複更新しない。
- 異なる確定結果の競合時は無条件に上書きせず、競合応答と照合方法を定義する。
- 成功応答は必要な保存完了後に返し、端末側の送信済み判断の根拠にする。
- 実際の発生日時とサーバ受信日時を分け、共通の日時形式とタイムゾーンを定義する。
- 結果確認状況を実行状態と分離し、結果待ち期限だけでrunningを失敗へ変更しない。
- 認証情報・登録コードを通常ログに出力しない。

## 次回アクション

登録CLIと管理画面の連携は[エージェント登録管理画面](../06_UserInterfaceDesign/3006_agent_registration.md)、
保存完了と登録受理の区別は[登録詳細設計](../02_SystemDesign/認証/0004_agent_registration.md)を参照する。
CLIとGUIで別々の端末登録APIを作成することは前提としない。

1. 登録・専用認証の方式と、応答消失時の端末確認方法を確定する。
2. 各APIの入力・出力・エラー・重複時の契約を個別設計へ展開する。
3. バックエンドとエージェント双方で、再送・再起動・照合を含む結合確認を行う。
