# エージェント事前登録・登録コード連携 詳細設計

## 目的

2026年9月13日の合意として、管理画面で作成した基本情報へ、登録コードを用いて実際の端末を紐付ける。
本書はバックエンド側の登録契約を定義する。2026年9月23日、端末マスタを起点とする登録・HTTP専用認証を実装した。
詳細な方式・実装範囲は[専用認証・端末認可](0005_agent_authentication.md)、パス・項目は[登録API](../../05_API_Design/API/0041_agent_registration_authentication.md)を参照する。MQTT認証は未構成。

## 対象操作

| 操作 | 内容 |
| --- | --- |
| 基本情報登録 | 管理画面でエージェント名・対象マシン等を登録する。 |
| コード発行・再発行 | 管理画面の操作を受けてバックエンドが生成し、管理画面に表示する。 |
| 端末紐付け | 端末からコードと端末情報を受信し、専用認証情報を発行する。 |
| 登録再試行 | 応答消失時に同じ登録要求を識別し、重複登録を防ぐ。 |
| 端末交換 | 管理画面で明示的に再登録を開始し、旧認証情報を失効させる。 |

## 管理項目

| 項目 | 内容 | 必須 |
| --- | --- | --- |
| エージェントID | バックエンドが端末マスタから初めてコードを発行するときにUUIDを採番する。 | 必須 |
| 基本情報 | エージェント名、対象マシンとの紐付け等。各項目の必須条件はAPI設計で確定する。 | 必須 |
| 登録コード | 対象エージェント、発行日時、有効期限、使用・無効化の状態を管理する。 | 発行時 |
| 登録要求ID | 端末が初回送信前に保存する、同じ登録試行を識別するID。 | 登録要求時 |
| 端末情報 | OS、ホスト名、エージェントバージョン等。 | 登録要求時 |
| 専用認証情報 | 対象エージェントと紐付けて管理する。外部API用のAPIキーとは別扱い。 | 登録成功時 |
| MQTTクライアントID | バックエンドが割り当て、端末が再起動・再接続後も同じIDを使用する。 | 登録成功時 |

## 処理詳細

### 1. 管理画面での事前登録とコード発行

| 項目 | 内容 |
| --- | --- |
| 入力 | 認証済み管理者による基本情報登録と登録コード発行操作。 |
| 処理 | 基本情報を保存して「端末未登録」とし、対象エージェント専用のコードを生成する。 |
| 出力 | 管理画面にコードと有効期限を表示する。 |

コードの有効期限は発行から30分とし、1端末の登録にのみ使用可能とする。
再発行時は以前の未使用コードを無効化する。照合失敗には試行回数制限を設ける。
コード生成・期限・状態の検証はバックエンドで行い、フロントエンドによる一致判定だけで登録を許可しない。

### 2. 端末登録

端末は入力されたバックエンドURLへ、登録コード、登録要求ID、端末情報をHTTPSで送信する。
コードの一致・期限・未使用・対象の登録可否を検証し、既存の基本情報に端末を紐付ける。
コード消費と紐付け・認証情報発行を整合させ、同じコードによる競合要求が複数端末を登録しないようにする。
新しいエージェント基本情報を毎回作成する処理にはしない。

登録成功後にエージェントID、専用認証情報、MQTTクライアントID、MQTT接続設定を返す。
通常のAPI利用では認証済みエージェントと操作対象の紐付けを検証する。
MQTTクライアントID自体を認証情報として扱わず、認証主体と利用可能なID・トピックを紐付ける。

### 3. 登録成功後の応答消失

#### 登録CLIとの連携（2026年9月14日追補）

端末登録は3OS共通のCLIから利用し、LinuxのCUIのみの環境にも対応する。
コマンド形式と管理画面の案内は[エージェント登録管理画面](../../06_UserInterfaceDesign/3006_agent_registration.md)を参照する。
CLIの引数・対話入力のどちらも同じ登録APIを使用し、コードをURLのパスやクエリへ含めない。
バックエンドURLの解決は端末側で行い、バックエンドは登録要求として受信した内容を検証する。

登録受理と端末の認証情報保存、API通信とMQTT接続の成功を区別する。
応答を返しただけでは端末の保存完了を確認できないため、管理画面へ保存完了と断定した状態を返さない。
認証情報は登録対象端末へ返し、管理画面で閲覧する情報とは分離する。
APIの詳細パス・項目は[登録API](../../05_API_Design/API/0041_agent_registration_authentication.md)で定義する。

#### 応答消失への対応

バックエンドで登録が成功しても、端末が認証情報を取得・保存する前に通信断が起こり得る。
同じ登録要求IDの再送では端末や認証情報を重複作成せず、同じ端末からの再試行と確認したうえで登録を完了できるようにする。
使用済みコードによる別端末の登録は許可しない。
登録要求IDだけを同じ端末であることの証明にはしない。
端末確認・資格情報復旧の方式と期限は[専用認証設計](0005_agent_authentication.md)を参照する。

### 4. 端末交換

管理画面で明示的に再登録を開始し、旧認証情報を失効させる。
既存のMQTT接続の切断・再接続拒否も含めた失効手順を詳細化する。
再発行したコードで新端末を登録し、古い端末が引き続き要求を処理できないようにする。

## 登録・更新判定

| 条件 | 処理 |
| --- | --- |
| 基本情報のみ登録済み | 端末未登録としてコード発行を受け付ける。 |
| 有効・未使用コードによる新規要求 | 事前登録された情報に端末を紐付ける。 |
| 同じ登録要求の再送 | 同じ端末かを確認し、登録済み結果の取得を復旧する。 |
| 別要求による使用済みコードの利用 | 拒否する。 |
| 登録済み端末の交換 | 明示的な再登録操作と旧認証情報の失効を必要とする。 |

登録完了と接続中は別管理とする。登録成功だけではOnlineにしない。
API・DBの状態コードは英語で定義し、日本語は画面表示ラベルに使用する。
無効化は状態更新で扱い、削除専用APIは作成しない。

## 入力チェック

| チェック | 内容 |
| --- | --- |
| 管理権限 | 基本情報の登録、コード発行・再発行、再登録の権限を確認する。 |
| コード | 一致、有効期限、使用済み・無効化状態を確認する。 |
| 試行制限 | コード照合失敗の回数を制限する。具体値・集計単位は専用認証設計を参照。 |
| 再試行 | 登録要求IDと同じ端末であることの確認情報を検証する。 |

## 出力

成功応答は必要な登録情報の保存完了後に返す。
認証情報と登録コードを通常ログに出力しない。
期限切れ・使用済み・再登録必要等を端末で案内できるエラー契約を定義する。

## 関連データ

| データ | 内容 |
| --- | --- |
| エージェント基本情報 | 管理画面で事前登録した管理対象。 |

| 認証情報・MQTT設定 | 登録済み端末の通信を許可するために利用する。 |
