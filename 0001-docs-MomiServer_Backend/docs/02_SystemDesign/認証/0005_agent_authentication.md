# Agent専用認証・端末単位認可 詳細設計

## 目的

2026年9月23日の実装として、端末マスタに紐付くAgentのHTTP認証、再試行、登録世代による認可を定義する。
基本フローは[登録設計](0004_agent_registration.md)、通信項目は[登録・認証API](../../05_API_Design/API/0041_agent_registration_authentication.md)を参照する。

## 対象操作

| 操作 | 内容 |
| --- | --- |
| コード発行 | 管理者が保存済み端末に対して要求する。バックエンドが暗号学的乱数32バイトをBase64URL化した43文字を発行する。 |
| 登録 | コード照合と端末鍵の保有証明後にAgent専用資格情報を返す。 |
| 更新 | 秘密鍵の保有証明と更新トークンの照合で、新しい資格情報へ交換する。 |
| 無効化・再登録 | 管理者の状態更新で資格情報を失効させ、再登録では登録世代を増やす。 |

## 管理項目

| 項目 | 内容 | 必須 |
| --- | --- | --- |
| deviceId | 端末マスタの既存数値ID。一端末に一Agent。 | 必須 |
| agentId | バックエンドが初回コード発行時に生成するUUID。端末マスタのIDとは別。 | 必須 |
| generation | 登録世代。初期値1、再登録開始ごとに増加する。 | 必須 |
| 端末鍵 | Agentが登録前にEd25519鍵ペアを生成・保存する。サーバーは公開鍵のみ保存する。 | 必須 |
| アクセストークン | 32バイト乱数の不透明Bearer。管理ユーザーJWTとは別物。 | 登録後 |
| 更新トークン | 32バイト乱数の不透明トークン。端末鍵と組み合わせて使用する。 | 登録後 |

## 処理詳細

### 1. 登録と応答消失

Agentは要求ID・秘密鍵・接続先・コードのSHA-256をJSONへ保存してから送信する。登録コードの平文は保存しない。
サーバーの使い捨てnonceを含むJWSで端末鍵の保有を確認する。IPアドレス、ホスト名、要求IDだけでは端末を認証しない。
登録行をロックし、コード消費・公開鍵の紐付け・資格情報保存・監査記録を同一トランザクションで確定する。
同時登録は一方のみ成功する。

同一コード・要求ID・公開鍵による再試行は、新しいnonceへの署名を必要とする。
登録成功時の応答を専用鍵によるAES-256-GCMで暗号化し、24時間だけ復旧可能とする。
同じ応答を返すため、復旧時点でアクセストークンが期限切れなら、受け取った更新トークンで更新する。
復旧期限切れ、鍵の喪失、登録後に更新済みの場合は登録応答を再取得できない。
既に保存済みの資格情報を使うか、管理者が再登録を開始する。

### 2. HTTP認証と更新

| 設定 | 初期値 |
| --- | --- |
| アクセストークン期限 | 15分 |
| 更新トークン期限 | 30日（更新成功から再計算） |
| 登録コード期限 | 30分 |
| nonce期限 | 2分、成功時に一度だけ消費 |
| 登録応答復旧期限 | 24時間 |
| 更新応答復旧期限 | 5分 |
| 登録・challenge・更新の要求制限 | 合算で接続元IPあたり毎分60回 |

トークン照合用にはSHA-256のみを保存する。復旧応答中のトークンは暗号化保存する。
更新には登録済み秘密鍵によるJWSを要求する。成功時にアクセストークンと更新トークンの両方を交換し、旧アクセストークンは直ちに無効になる。
旧更新トークンは同一更新要求ID・同じ鍵・新しいnonceの場合のみ、5分以内に同一応答を返す。
別要求ID、別鍵、復旧期限経過後の旧更新トークンでは更新しない。現在の更新トークンを持つ正規端末の資格情報を、署名失敗だけで失効させない。

要求回数をDBへ原子的に加算する。アプリケーションは任意のX-Forwarded-Forヘッダーを信用しない。
プロキシ配下で接続元が集約される場合は入口のレート制限と信頼済み転送設定を別途調整する。
nonce、古い要求回数、期限切れ復旧応答は1時間ごとに清掃する。清掃前でも期限を過ぎたデータは受理しない。

### 3. 端末単位の認可

認証済みAgentをUUID・端末ID・登録世代からなる専用主体とし、ROLE_AGENTだけを付与する。
アクセストークンはAgent API内だけで認証する。管理画面APIへ転用できず、管理者JWTや外部APIキーでもAgent APIを利用できない。
毎回、資格情報の期限・失効・Agentのregistered状態・端末マスタが無効状態0でないことを検証する。

既存バッチのtarget_agent_idは端末マスタの数値IDとして扱い、外部Agent UUIDと混同しない。
新しい実行要求には、作成時点の登録世代をtarget_agent_generationへ保存する。
開始・完了・状態照会・ファイル一覧・取得は端末IDと登録世代の両方を照合する。別端末と未存在はいずれも404とする。
開始・完了の認可と結果更新は同一トランザクションで行い、途中の無効化・再登録を行ロックで排他する。
登録世代のない過去要求や未登録時の要求を、新しい端末へ自動付与しない。管理者が必要性を確認して新しい実行IDを作成する。

### 4. 無効化と再登録

status=disabledで現在の資格情報と復旧応答を失効させる。status=pendingで旧資格情報を失効し、登録世代を増やして新しい登録待ちにする。
同じAgent UUIDを維持し、MQTT Client IDは登録世代を含む値へ変更する。
更新には理由を必須とし、管理者・対象Agent・世代・操作・時刻を監査テーブルへ保存する。
端末マスタの状態0では認証を拒否する。恒久的な資格情報失効にはAgentの無効化・再登録を使用する。
実行中のOSプロセスは認証失効だけでは停止できない。キャンセル・停止確認は別処理とする。

### 5. MQTTの境界

2026年9月23日、MQTTブローカーは当面Eclipse Mosquittoを採用することに決定した。
Dynamic Securityによる専用連携を実装した。既定は無効であり、運用者がプラグイン・管理接続・配信用ユーザーを構成する。GET /api/v1/agent/mqtt/settingsで現在世代の設定を取得し、readyのときだけ専用秘密情報を返す。登録応答中のmqttは初期状態であり、常駐処理は設定取得APIを使用する。
AgentMqttProvisioningは永続化した資格情報を5秒周期で同期する。無効・旧世代の資格情報を先に失効し、新世代を有効化する。HTTP失効からブローカー反映までは時間差があるため、命令内容取得時にもHTTP認可を実施する。
導入方法と実装範囲は[Agentバッチ実行・Mosquitto運用](../../07_OperationsDesign/0004_agent_batch_runtime.md)を参照する。

#### Mosquitto連携の実装案

以下の方針に基づき実装した。実際のAPI・状態は[常駐API](../../05_API_Design/API/0042_agent_runtime.md)を正とする。

- Dynamic Securityプラグインによって、稼働中に端末別の認証情報とACLを管理する。Mosquitto 2.0以降で利用できるが、明示的な有効化が必要となる。
- Agentの登録世代ごとに専用ユーザー・パスワードを発行し、既存のMQTT Client IDに拘束する。HTTPトークンやバックエンド用の共有資格情報をAgentへ流用しない。
- ACLは既定拒否とし、当該Agent・登録世代の命令／キャンセルトピックの購読と受信だけを許可する。Agentからの送信は実装する報告トピックだけに限定する。管理用制御トピックへのアクセスは許可しない。
- 無効化・再登録時は旧ユーザーを無効化する。Dynamic Securityの無効化は既存接続の切断と再接続拒否を伴う。HTTP側の失効とブローカー側の反映完了は別々に確認する。
- ブローカー停止時にも処理要求を失わないよう、登録・失効の同期要求をDBへ永続化して再試行する。反映未完了を管理画面へ表示し、旧世代の失効確認と新世代の設定完了まで新たな命令配信を許可しない。
- 管理用接続と通常の命令配信用接続の権限を分離し、Agent接続にはTLSとサーバー証明書検証を使用する。

根拠: [Mosquitto公式 Dynamic Securityドキュメント](https://mosquitto.org/documentation/dynamic-security/)。対象バージョンの初期化方法・既定ACLを確認し、購読許可とメッセージ受信許可の両方を検証する。

既存のローカル構成（`mosquitto/compose.yml`）は2.0系イメージを指定し、`mosquitto/config/mosquitto.conf`はパスワードファイルと静的ACLを使用している。これはAgent登録APIとの自動連携を意味しない。
現在の静的ACLの`momi/#`と既存バッチ命令の`smarthome/agents/...`には差があるため、移行時に名前空間と登録世代の表現を確定し、既存IoT通信への影響も確認する。
稼働環境への適用前に、正規端末の接続・他端末トピック拒否・Client ID不一致拒否・接続中の失効・旧世代の再接続拒否・ブローカー停止からの同期復旧を結合検証する。

## 入力チェック

通信はHTTPSを前提とする。CLIは通常HTTPを拒否するが、開発用`--allow-insecure-localhost`を明示した場合のみlocalhost・127.0.0.1・[::1]へのHTTPを許可する。許可は保存せず各操作で必要となる。開発用HTTPではプロキシを使わず、localhostはDNSを介さず127.0.0.1へ接続する。
接続先への認証情報埋め込み、クエリ・フラグメント、リダイレクトは引き続き拒否する。
Agent側の操作手順とMQTT対応の実装順序はAgent設計リポジトリの`docs/07_OperationsDesign/010_registration_test_guide.md`を参照する。
バックエンドをHTTP待受にする場合は、信頼したTLS終端の背後に限定して直接公開しない。
Agentの保存済み接続先が変わる場合、既存資格情報を別サーバーへ送らず明示的な再登録を要求する。

## 出力

資格情報とnonceの応答はCache-Control: no-storeとする。登録コード・トークン・秘密鍵・JWSを通常ログや監査理由へ記録しない。
管理画面は登録状態・登録世代・最終認証確認を表示し、資格情報は表示しない。
GET /meでlast_seen_atを更新する。これは監視ハートビートの実装やOnline判定を意味しない。
