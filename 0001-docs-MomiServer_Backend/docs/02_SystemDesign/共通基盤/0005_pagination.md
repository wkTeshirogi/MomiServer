# 共通ページング基本設計

## 概要

既存の件数制御・先読み・ページ組立てを共通化し、公開APIごとの契約は維持する。

## 目的

検証や次ページ判定の重複を減らし、総件数・取得上限の保守箇所を明確にする。

## 対象範囲

| 区分 | 内容 |
| --- | --- |
| 対象 | 通知、APIアクセスログ、バッチ実行ログ、外部在庫API |
| 対象外 | APIレスポンス変更、全マスタのサーバー側ページング化、検索条件・並び順・認可の変更 |

## 全体構成

API固有条件の検証から共通Paginationによる開始位置・件数検証へ進み、Repositoryへ問い合わせる。
先読み行と同じ条件の総件数からPageSliceを生成し、既存の公開DTOへ変換する。

## 構成要素

| 構成要素 | 役割 |
| --- | --- |
| Pagination | offset、範囲指定・選択肢指定のlimit、補正、先読み件数 |
| PageSlice | 表示行、次ページ有無、DB照会の総件数を保持する不変の内部ページ |
| 各Service | 上限・補正か拒否かの方針、文言、業務条件を保持 |
| 各Repository | 認可・検索条件・順序・先読み・総件数のSQLを保持 |

## 主要処理

| API | 既存方針 |
| --- | --- |
| 通知 | 未指定20件。指定値は1～100へ補正。負のoffsetは拒否 |
| APIログ | limitは1～200。負のoffsetは拒否。検索期間等も従来どおり検証 |
| バッチ実行ログ | limitは20・50・100。負のoffsetと不正な日付・時間条件を拒否 |
| 外部在庫 | limitは1～100、offsetは0以上。それ以外を拒否し、英語の既存文言を維持 |

## データ方針

| データ | 方針 |
| --- | --- |
| 先読み | 表示件数より1件多く取得。件数加算で整数がオーバーフローしない |
| 次ページ | 先読み結果が表示件数を超えるかで判定 |
| 総件数 | DBのcount結果を維持。ページ外の空結果でも総件数を0へ推測し直さない |
| 行 | 内部ページは防御コピーし、外部から変更できない |
| 公開形式 | logs・has_more・total_count等の既存プロパティを変更しない |

## エラー方針

既存のIllegalArgumentExceptionとAPI固有文言を維持する。
共通化のために全APIの上限や件数補正方法を一律化しない。

## 画面側の共通動作

- 画面の初期表示は20件、選択肢は20・50・100件とする。件数と選択欄は一覧ヘッダーの上、前後移動は下に配置する。
- クライアント方式は検索文字列を共通フックのリセットキーへ渡し、検索条件変更時は件数が十分あっても先頭へ戻す。
- データの再取得だけでは先頭へ戻さず、件数減少で範囲外となった場合に有効なページへ補正する。
- APIログと実行ログはサーバーの総件数で範囲外を判定し、先頭ページを再取得する。旧位置の空ページを確定しない。
- ユーザー・端末一覧は取得失敗を上部へ通知し、以前の正常行を保持して再読込できる。正常な0件と取得失敗を区別する。
- APIキーの発行・無効化中は検索・件数変更・前後移動を無効化する。アラートの更新中制御も維持する。
- スケジュールカレンダーは全定義を検索してページ分割する。件数の単位は「定義」と明記し、期間内のカード数・実行回数とは区別する。
