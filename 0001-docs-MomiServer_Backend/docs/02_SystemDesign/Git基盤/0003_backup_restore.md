# Gitバックアップ・復元基本設計

## 概要

Gitの全体保存領域と管理DBを同じ整合点のバックアップセットとして扱う。
頻度・復旧目標・暫定保存先は[本番運用設計](../../07_OperationsDesign/0005_production_acceptance.md)を正本とする。
GitHubのmirrorやソース保管だけではDB・権限・削除状態・秘密情報を復旧できない。

## 目的

月次フルと週次差分から、repo ID、Git全ref、管理状態を対応付けて検証し、安全に公開再開できるようにする。
本書は方式と受入条件の基本設計であり、取得スクリプトや本番復旧手順の実装・実証ではない。

## 対象範囲・構成要素

| 資産 | 取得・復元方針 |
| --- | --- |
| 管理DB | Gitメタデータ、利用者・ACL・PAT、保護規則、操作予定・監査・Outboxを含むアプリDB全体 |
| bare repo | HEAD、全refs、packed-refs、objects、reflog、管理対象config。論理削除猶予内のrepoも含む |
| 配置・設定 | 相対格納キー、設定の版、アプリ・JGit・DB版、実行ユーザーと所有権、必要な復元パラメーター |
| 秘密情報 | DB接続・暗号化鍵・証明書等を別管理。暗号化バックアップを復号する鍵を同じ媒体だけに置かない |
| 除外 | lock・受信中一時領域、任意hook、CI成果物、Agent保持データ。別機能の保護要件は維持 |

単なるcloneやbundleは管理DBを含まず、bundleは到達可能なref・object以外の状態も網羅しないため、
完全復旧セットの代替にしない。[Git公式bundle仕様](https://git-scm.com/docs/git-bundle)を参照する。
bareの保存対象は[Git公式レイアウト](https://git-scm.com/docs/gitrepository-layout)に基づく。
未知ファイル・外部参照・残存lockを検出した場合、無条件にコピー・除去せず異常として確認する。

アプリDB全体を復元する場合、他機能の添付等も同じ整合点の運用バックアップと組み合わせる必要がある。
これらの取得詳細は運用設計側の責務であり、GitファイルとDBだけでアプリ全体を復旧可能とは扱わない。

## データ方針

### セットとマニフェスト

| 項目 | 内容 |
| --- | --- |
| 識別 | backup ID、形式版、full/differential、取得開始・整合点・終了日時 |
| 関係 | 基準full ID、DBアーカイブID、アプリcommit、DB migration版、Git/JGit・DBバージョン |
| repo一覧 | repo ID、格納キー、lifecycle・health、メタデータ版、SHA-1形式 |
| refs | 全ref名と参照先object ID。annotated tagのobject IDと必要なpeeled IDを区別 |
| HEAD | symbolic参照先または直接OID。空repoは未作成mainを指す状態を明示 |
| ファイル | 正規化した相対パス、種別、長さ、SHA-256、追加・変更・削除。絶対パス・リンクは禁止 |
| 完了状態 | checksums、DB検査結果、ref検査結果、完了マーカー、保管場所・取得者、失敗理由 |

refの値は必ずしもcommitではない。タグobjectをcommit SHAへ置換して一致扱いにしない。
マニフェストにはPAT原文や鍵・接続パスワードを記載しない。
ハッシュだけでは悪意ある改ざんを防げないため、保存先の書込制限を設け、外部退避時の暗号化・真正性保護も検討する。
不完全なセットは復元候補へ表示しない。

### フルと差分

月次フル・週次差分に加え、2026/10/29に次の比較元・DB取得方式をユーザー確認して確定した。

- 月次フルはDBの完全な論理アーカイブと全bare repoファイルを取得する。
- 週次は直近の正常な月次フルを比較元とする差分とし、前週差分への連鎖は作らない。
- Git差分には基準フルから変化したファイルの全内容、追加repo、削除・移動の情報を含める。
- 変更判定は内容ハッシュを使用し、mtimeだけでobject・refの変更を省略しない。
- DBは週次でも完全な論理アーカイブを取得する。SQL文同士の差分やDBファイルの稼働中コピーは行わない。
- 復元は基準フルと選んだ週次差分を組み合わせ、その週次に対応するDBアーカイブを使う。
- 差分取得前に基準フルの存在・検証状態を確認する。欠落時は正常扱いせず、新規フルを取得する。
- repackでpack全体が変わると差分容量が大きくなる。正確性を優先し、実測後に最適化する。

連鎖型増分へ変更する場合は、必要な全世代、削除記録、復元順序、失敗時の依存関係を再設計する。

### 取得日時と重複時の優先順位

日時はAsia/Tokyoを基準とし、次の順序で予定種別を判定する。

| 条件 | 実行する取得 |
| --- | --- |
| 毎月1日03:00 | 月次フル |
| 毎週月曜日03:00、かつ1日ではない | 週次差分 |
| 1日が月曜日に重なる | 月次フルのみ。週次差分は実行しない |

月次フルを廃止する意味ではなく、重複する週次差分を中止する方針としてユーザー確認済みとする。
03:00は取得処理の開始予定時刻であり、完了待ちを経たBEの実停止時刻・停止時間を保証する値ではない。
月次と週次を別々に起動して先着順の排他だけに任せず、予定日時から月次を優先選択してから取得を開始する。
予定日時に対する重複起動も防止し、実開始が遅れても選択済みの取得種別を変えない。
本書は運用仕様の記録であり、systemd timerやアプリのSchedulerを登録したものではない。

## 主要処理

### 取得と整合点

初期方式は無停止取得ではなく、専用スクリプトから保守制御・systemd停止を組み合わせる。
Git repoだけ止めても共通ユーザー・PAT・ACL更新が進むと整合点がずれるため、BEの全書込みを止める。
BE停止時間は30分以内を目標とする。固定の強制終了時刻ではなく、実際の停止時間は導入前に測定する。
保守・復元モードは復元対象DBの過去状態だけに依存させず、運用側の永続的な起動制御でも保持する。
再起動やDB復元でこの制御を暗黙解除しない。管理Webの復旧操作とGit受付の再開許可を分離する。

1. 取得ID、保存領域、基準フル、容量、排他状態を確認する。前回の保守状態を無条件に解除しない。
2. 新規バッチ開始・自動配信とGit新規書込みをdrainにし、進行中バッチ・Git書込みの完了を待つ。
3. Git未完了操作を照合する。解消不能なら取得を中止し、整合したセットと称しない。
4. BEを正常停止し、GC・復元・外部直接書込みもないことを確認して整合点を固定する。
5. 単一アプリDBをpg_dumpのアーカイブ形式で取得する。DBロール等の復元情報は別の保護設定として管理する。
6. Gitの対象一覧・HEAD・全ref・ファイルを採取し、フルまたは差分を別の一時出力先へ作成する。
7. DBアーカイブの検査とref一覧・ファイルハッシュの再照合を行い、完了マーカーを最後に付ける。
8. 取得結果を永続化し、BE起動後の点検を経てdrainを解除する。失敗時も原因確認後に再開を判断する。

BE停止後はAgent結果を受け取れないため、既存方針どおりAgentが保持し、起動後に受理・重複判定する。
取得開始を理由に実行中バッチを強制停止しない。drainが異常終了する等で成立しない場合は取得延期・失敗として通知する。
pg_dump自体のDB内整合性とGitを含む整合点は別であり、後者は書込停止で保証する。
[PostgreSQL公式pg_dump仕様](https://www.postgresql.org/docs/17/app-pgdump.html)を参照し、実DB版に合うクライアントを使用する。
PostgreSQLコンテナ自体の稼働中データディレクトリを、そのままファイル差分で取得しない。

### 停止時間・容量確認・再開

- 03:00にdrainを開始し、実行中処理の完了待ち中はBEと結果受信経路を維持する。
- 待機やBE停止が30分を超えた場合は通知し、時間超過だけでバッチ・Git・取得処理を強制終了しない。
- バックアップ前に今回の出力・検証・復元作業用の必要容量と安全余裕を確認する。
- Gitの新規push停止閾値50 GiBを満たすだけで、バックアップの容量が足りるとは判定しない。
- 通常終了として扱える取得失敗でも、稼働DB・Gitが正常なら確認後にBEを再開し、通常の容量保護を適用する。
- DB・Git自体の異常や整合性不明があれば、自動的に書込みを再開せず管理者判断を待つ。
- スクリプト強制停止等で結果不明の場合は、永続保守状態を維持して確認する。単純な再起動で解除しない。

### 再実行・未取得予定の補完

| 事象 | 合意した動作 |
| --- | --- |
| 一時的な取得失敗 | 失敗終了から60分後、最大2回再試行。初回と合わせ最大3回 |
| 容量不足・破損・設定不正 | 自動再試行せず通知し、原因解消後に手動実行 |
| 月次フル失敗 | 再試行もフル。同日の週次差分へ自動変更しない |
| 停止中に未開始の予定が発生 | 復帰後に1回だけ補完し、期限到来した月次が未成功ならフルを優先 |
| 補完する復旧点 | 実際の取得時点。停止中の過去の各予定時点を復元できる取得物とは扱わない |

前回が終了していない間は再試行を開始しない。元の予定・取得種別と試行回数を保持し、重複取得を防止する。
再試行は新しい整合点で取得し、不完全な取得物へ無条件に継ぎ足さない。
停止中の未開始予定の補完と、失敗済み予定の再試行を区別する。
再起動を理由に自動再試行回数をリセットしたり、上限超過した失敗を未開始扱いにしたりしない。
補完では過去の全予定を連続取得せず、復帰時点の1セットにまとめる。
Agent未送信結果の無期限保持・回数上限なしの再送とは別の処理であり、その既存方針は変更しない。

### 保管と清掃

| 対象 | 合意した保持条件 |
| --- | --- |
| 月次フル | 正常なものを直近3世代 |
| 週次差分 | 正常なものを直近8世代 |
| 差分が依存するフル | 世代上限を超えても、その差分を保持する間は保存 |
| 更新直前の別取得 | 更新後の動作確認完了後も7日間保持 |

世代は成功した取得を単位とする。取得失敗・未実行・重複日スキップを成功世代として数えない。
世代数は取得成功回数であり、常に厳密な3か月・8週間を保証する期間指定ではない。
repoの利用状況がinactiveやnever_usedでも対象から除外せず、管理対象全体の復元可能性を維持する。

- 不完全セットと正常セットを分離し、失敗時は既存正常世代を削除しない。
- 基準フルを参照する週次差分が残る間は、そのフルを削除しない。月替わりでも依存関係を維持する。
- 通常一時ファイルの24時間削除、監査1年保持とは別に、バックアップの世代規則で清掃する。
- repo物理削除の前提となるバックアップは、猶予期間・復元可能期間と対応するものを残す。
- 初期の同一サーバー内保管はディスク故障・侵害への完全な保護ではない。NAS等の準備後に外部退避を確認する。
- 取得日時・月次優先・保持世代・暫定保存先・停止目標・再実行条件は決定済み。
- 正式配置と権限は[本番運用設計](../../07_OperationsDesign/0005_production_acceptance.md)に従う。外部退避先の準備は残件とする。

repoの自動清掃を当面行わない方針と、バックアップの世代整理は別の機能として扱う。
いずれも本書で実装・有効化したものではなく、バックアップ清掃には依存関係の検証を必須とする。

### 別領域復元と公開再開

1. サービスを停止し、対象整合点と対応アプリ版を選ぶ。現在の障害領域を上書きせず保全する。
2. 外部送信・Job実行・Git受付を停止した隔離環境へ、基準フルと対象差分を展開する。
3. パス・ファイル種別を検証し、削除一覧も反映して全ファイルをマニフェストと照合する。
4. 対応するDBアーカイブを別DBへ復元し、migration版、repo ID、ACL、削除状態、操作予定を確認する。
5. 全refのobject ID、HEAD、annotated tag、空repoを照合し、全repoのfsckを実行する。
6. 復元されたGit PATをすべて失効し、一回限り例外許可もすべて無効化する。新しいPATの発行を別操作にする。
7. 未処理Outboxは保留し、すでに外部処理済みのイベントが再配信されないか照合する。
8. システムADMINが利用者・ACL・保護規則・整合性を確認してから、DBと保存ルートを組として切り替える。
9. 初期は読み取り確認を行い、問題がないことを承認して新規書込み・後続処理を再開する。

復元時のGit PAT失効はユーザー合意事項とする。古いバックアップから過去の失効状態を取り戻す方式に依存しない。
失効がDBへ確定する前にGitエンドポイントを起動しない。検証用復元でも本番向けSecretで外部接続しない。
復元後に権限や通常のWebセッションが過去状態へ戻る問題は、アプリ全体の復旧受入で別途確認する。
Git PATの失効だけで、全認証方式のロールバック問題を解決したとは扱わない。

データ損失は選んだ整合点以後に発生し得る。復元後のGitを自動でクライアントへforce pushさせない。
取得後に失われたcommitは利用者のclone等から調査し、必要な履歴は管理者確認後に回収する。
Outboxの外部処理済み状態までバックアップで過去へ戻るため、外部受信側の重複判定・照合が必要になる。

## 状態遷移・エラー方針

| 状態・事象 | 動作 |
| --- | --- |
| preparing / draining / capturing / verifying | 同時取得・復元・GCを拒否。完了まで正常世代にしない |
| completed | ハッシュ・DB・refの取得検証済み。実際の復元試験済みかは別属性で管理 |
| failed | 理由・段階を記録し管理者へ通知。正常世代を保全し、成功とみなさない |
| restore_verifying | Git受付・外部イベント配信を停止。検証失敗なら隔離を維持 |
| DBだけ・Gitだけ成功 | セット全体を失敗扱いとし、片側だけを復旧点として採用しない |
| 差分欠落・ハッシュ不一致 | 展開・公開を中止し、別の正常な整合点を選ぶ |
| 停止後にスクリプト中断 | 保守状態と取得IDを残す。再起動だけで自動公開せず、運用者が状態確認する |

## 実装時の受入条件

| ID | 確認内容 |
| --- | --- |
| GB-01 | 作成・push・削除・GC・ユーザー権限変更と取得を競合させ、整合点を固定できる |
| GB-02 | 月次フルと週次差分を別領域へ復元し、DB、全ref、HEAD、tag、ファイルを一致確認 |
| GB-03 | 差分の追加repo・論理削除・物理削除・repack・空repo・変更なしrepoを復元できる |
| GB-04 | 容量不足、dump失敗、途中停止、差分欠落、改ざんで正常世代を壊さず停止できる |
| GB-05 | 全Git PATと例外許可の失効、ACL確認、Outbox保留前には外部公開しない |
| GB-06 | CentOS上の所有権・SELinux・systemd・実DBで復元し、保守時間と復旧目標を測定する |
