# Gitストレージ・操作整合性基本設計

## 概要

単一Backendが管理するローカル永続領域へbare repositoryを保存し、管理DBと内部IDで対応付ける。
管理者の手動Git操作、同期ソフト、Agent、別Backendが同じ領域へ直接書き込む構成は認めない。

## 目的

名称変更で保存先が変わらず、作成・push・削除中に障害があっても、Gitの確定結果と実行者を追跡可能にする。

## 対象範囲・構成要素

| 要素 | 責務 |
| --- | --- |
| Repository管理 | URL名・所属グループと不変の内部IDの解決、状態と版の管理 |
| Storage管理 | 内部IDからの保存先解決、bare作成、容量、整合性確認 |
| Git受付 | JGitのUploadPack・ReceivePack、認可、ref検証、Git応答 |
| 操作予定・監査 | DBへ保存した予定とGitの結果を照合し、確定イベントを冪等に補完 |
| 保守制御 | push・削除・GC・バックアップ・復元を排他制御 |

CI/CD実行、同期先GitHub、Discord送信の成功はGit操作の成功条件に含めない。

## データ方針

| 論理データ | 主な情報・制約 |
| --- | --- |
| グループ | 内部ID、親グループID、URL名、表示名、状態。循環した親子関係は禁止 |
| Repository | 内部ID、グループID、URL名、説明、既定branch、状態、版、作成更新・削除情報 |
| Storage状態 | 相対格納キー、形式、容量、空き容量、最終アクセス・push・点検成功日時、異常理由 |
| 利用状況 | 最終作業日時、利用状況status、最終判定日時。取得アクセス日時とは分離 |
| 操作予定 | 操作ID、repo ID、実行者、PAT ID、種別、全refのold/new OID、認可版、状態・日時 |
| 監査・Outbox | 操作ID、ref、old/new OID、結果、理由、イベントID、日時。配信状態の詳細は別設計 |

Repository、操作予定、監査などの名称は論理名であり、テーブル名・カラム・DDLは詳細設計で確定する。
DBアクセスは既存方針どおりjOOQとし、認可・状態更新・監査はサービス層の共通境界へ集約する。

### 物理配置と名前

- 保存ルートはapplication.yamlの専用設定とし、配布物・一時領域・Web公開ディレクトリから分離する。
- 相対格納キーはサーバー生成UUIDを固定形式へ変換した値だけで構成する。URLや表示名を連結しない。
- 例示する配置は`repositories/<内部ID>.git`、作成中は同一FS上の`staging/<操作ID>`とする。
- 正式なGit保存先・作業領域は[本番運用設計](../../07_OperationsDesign/0005_production_acceptance.md)を正本とする。
- Git・作業・バックアップを置く/optが未マウントの場合、別FSへ誤書込みしないよう起動・取得を拒否する。
- rename・所属変更で物理配置を変えない。URLの旧名転送は初期対応せず、旧URLは404とする。
- URL名は小文字ASCII英数字・ハイフン・アンダースコアを基本とする。長さ・予約語は詳細設計で固定する。
- URL名の正規化後の一意性をDB制約で保証する。グループ階層とrepo名を別要素として解決する。
- dot segment、空要素、不正escape、区切り文字の多重符号化、予約サービス名は入口で拒否する。
- 解決後の実パスが保存ルート配下にあることを検証し、途中・末端のsymlinkやjunctionも拒否する。
- Gitの内部参照でも外部objectに到達させない。alternates、外部worktree、外部include設定を受け付けない。
- データ領域は専用実行ユーザーのみ書込可能とする。repo内hookは実行せず、管理されたJGit処理だけを使う。

パス検査後に別主体がリンクへ差し替えられる構成は認めない。権限・単一書込主体・操作中排他を併用する。
侵害済みOS管理者までアプリのパス検査で防げるとは扱わない。

## 状態遷移

ライフサイクルと健全性を別々に保持し、復旧待ちと利用停止を混同しない。保存値は英語とする。

| lifecycle | 意味・主な遷移 | Git取得 | push |
| --- | --- | --- | --- |
| provisioning | 作成中。成功でactive、失敗は点検待ち | 不可 | 不可 |
| active | 通常。disabled・delete_pendingへ変更可能 | 権限に従う | 健全性・権限・保護規則に従う |
| disabled | 管理上の停止。確認後activeへ | 不可 | 不可 |
| delete_pending | 論理削除。猶予内はrestoringへ、条件成立後deletedへ | 不可 | 不可 |
| restoring | 復元検証中。成功後activeまたはdisabledへ | 不可 | 不可 |
| deleted | 物理削除済みの管理記録。IDを再利用しない | 不可 | 不可 |

| health | 動作 |
| --- | --- |
| ready | lifecycleと保守状態に従う |
| capacity_low | push停止。読み取りが安全な場合だけ取得継続 |
| audit_pending | ref更新後のDB記録待ち。次の書込み停止、取得は継続可能 |
| missing / corrupt / unknown | Gitアクセス停止、管理者確認。片側だけの実体を自動削除しない |

サービス全体の`running / draining / readonly / stopped / restoring`を併用する。
サービス・repo・権限・容量のうち最も制限の強い条件を採用し、ADMINでも障害状態を自動迂回しない。

## 主要処理

### 作成・変更・削除

1. 作成権限、所属、名前、空き容量を検証し、内部IDとprovisioningをDBへ保存する。
2. stagingでbareを作成し、SHA-1形式、HEADの`refs/heads/main`、外部参照なしを検証する。
3. 同一FS内の原子的renameで本配置へ移し、DBをactiveへ確定して監査する。
4. 中断時はDB状態・操作ID・配置先を照合して再開する。存在する実体を無条件に上書きしない。

名称・所属変更は認可を再評価してDBを更新する。所属移動は移動元と移動先の管理権限を要求し、
移動先の継承権限へ切り替わるため、権限の増減と処理中pushを排他して監査する。
既定branch変更はHEADとの整合も操作予定を使って補完する。
削除はdelete_pendingへの変更のみとし、即座に新規アクセスを拒否する。
物理削除は猶予・バックアップ成功・管理者確認を満たす別の保守処理とし、監査とtombstoneは保持する。

### 排他とpushの確定

repo単位の書込リースを、push、作成完了、HEAD変更、無効化、削除、復元、GCで共用する。
pushのdiscovery GETと本体POSTは別要求として認可し、GETからクライアント待ち全体をロックしない。
受信開始後もref確定直前に認証・認可を再確認する。長時間DBトランザクションをpack受信中に維持しない。
認可変更は[認証・認可設計](./0002_authentication_authorization.md)の確定境界に従う。

1. POST認証後に書込リースを取得し、未完了操作、状態、容量と同時受信枠を確認する。
2. JGitでpackを検証する。ref確定前に全コマンド、old OID、保護規則、認可の現行版を再検証する。
3. 全refのold/new OIDと実行者を持つ操作予定をDBへ先行コミットする。失敗したらrefを更新しない。
4. JGitのref更新を実行する。複数refはatomic更新を必須とし、非atomicの複数ref要求は拒否する。
5. 成功refの監査、完了状態、Outboxを同一DBトランザクションで保存してリースを解放する。

Gitのatomic能力は技術検証済みだが、単なるpre-receive全件検証だけでは原子的更新の保証にならない。
実装時はJGitの実行結果と全refを照合する。クライアントには複数ref送信時のatomic要求を案内する。
通常のGit CAS競合は拒否し、別のpushで変わったrefを強制上書きして再実行しない。

### ref確定後のDB障害・応答障害

| 段階 | 対応 |
| --- | --- |
| 操作予定確定前 | refは変更しない。DB復帰後にクライアントが再送可能 |
| 予定確定後・ref未確定 | 予定と実refを照合。oldのままなら未適用として確定し、refを勝手に進めない |
| ref確定後・完了保存失敗 | Gitを巻き戻さない。未完了予定を残し、次の書込みを拒否して補完する |
| 成功応答だけ喪失 | Git側は成功済みの可能性がある。再送を新規成功イベントとして二重記録しない |
| 照合で第三のOID・部分更新 | 自動判断せずreadonly相当で隔離し、Git結果・reflog・操作予定を管理者が確認 |

再起動時と定期照合時に未完了予定を回収し、全refが期待newなら監査・Outboxを補完する。
中間OIDが別pushで消えないよう、未完了予定があるrepoでは次のref更新・GC・物理削除を許可しない。
空リポジトリの不存在refはold/newのゼロOIDとして区別する。
イベントの一意性は操作IDとrefを基本に、repo ID・old/new OID・種別も照合する。
同じOIDへの正当な再作成を永久に重複除外しないため、OIDだけを全期間の一意キーにしない。

## 容量・保守方針

### 履歴保持と容量指標

| 対象 | 合意した扱い |
| --- | --- |
| 現在のbranch・tagから辿れる履歴 | repoを物理削除するまで保持。経過日数や容量超過を理由に切り詰めない |
| branch削除・履歴書換えで参照されなくなった履歴 | 永久保存は不要。復旧猶予と安全条件を満たした後に清掃可能 |
| 現行ファイルの論理容量 | 既定branchの最新treeのファイルサイズ合計として、履歴込みの実使用容量と分けて管理 |
| Gitの実使用容量 | 全branch・履歴・Git管理情報を含む保存領域の実使用量として監視 |
| バックアップ容量 | Gitの稼働領域とは別の指標として管理し、世代と復元依存関係に従う |

最新ファイルと履歴はGit objectを共有するため、上記指標は物理領域の完全な分離や単純な足し算を意味しない。
論理容量だけでディスクの安全性を判定せず、履歴を含む実使用量と作業領域・空き容量も確認する。
参照されなくなった履歴の清掃では、別branch・tag・reflog、未完了操作の保護対象を確認する。
容量不足時は警告・新規push停止で保護し、保持対象の履歴を自動削除して空きを作らない。
先に提案した1repo 10 GiBは採用せず、固定容量上限なしと空き容量保護を組み合わせる。
repoの論理削除猶予は30日、参照されなくなった履歴の復旧猶予とreflog保持は90日で合意した。
reflogは到達不能分も90日保持する。通常のbranch・tagから辿れる履歴の保存期限を90日にする意味ではない。
参照喪失からの復旧猶予を、objectファイルのmtimeだけで保証できるとは扱わない。
将来の清掃実装では起点・保護参照・未完了操作を確認し、猶予とバックアップ条件を満たしてから削除する。
当面は状態管理のみとし、日数到達による自動物理削除・pruneは有効にしない。

### 共通設定による変更

Gitの容量・受信制限はADMIN向け共通設定で変更できる設計とする。既存の他カテゴリ設定の保存契約は変更しない。
未利用判定の期間も共通設定で変更可能とし、設定の永続化・版管理・APIは詳細設計で定義する。
設定変更の操作者・日時・変更前後を監査し、下限・上限・単位と設定間の矛盾を保存時に検証する。
制限の変更は次の要求から適用し、処理中の操作を変更だけを理由に強制中断しない。
処理中の要求は受付時の制限設定版を使い、ref確定時には実際の空き容量・認可・障害状態を再確認する。
上限の引下げで既存量が超過しても履歴を削除しない。初期制限値は次節の合意値を使用する。

### 初期制限値

2026/10/29に提示された導入予定サーバーの容量を踏まえ、次の初期値を合意した。
固定容量上限なしは、設定値の欠損やディスク保護の無効化とは区別する。

| 項目 | 初期値・意味 |
| --- | --- |
| 現行ファイルの論理容量上限 | 固定上限なし |
| 履歴込みのrepo・Git全体容量 | 固定上限なし。保存先FSの空き容量で保護 |
| 1回のpush | 受信pack全体512 MiBまで |
| 単一object | 展開後50 MiBまで |
| 同時push | 全体2件、同一repo1件 |
| 空き容量警告 | Git保存先/optの空き100 GiB未満 |
| 新規push停止 | 同FSの空き50 GiB未満 |
| 無通信タイムアウト | 5分 |
| 操作全体の時間上限 | 固定上限なし。無通信・容量・認可等の拒否条件は維持 |

容量・転送量は二進単位で扱い、1 GiBは1024 MiBとする。
旧案の空き容量20%・10%や20 GiB・10 GiBによる条件は採用せず、この合意値へ置き換える。
受信pack量とobject展開後サイズを別々に確認し、プロキシのHTTP本文制限には制御データ分も考慮する。
Servlet・プロキシの時間制限も、無通信5分と操作全体の固定上限なしに矛盾しないよう構成する。
空き容量判定は実配置先FSで行い、パス未マウント時のルートFSの空きを代用しない。
同時受信の予約量・展開中の容量計測方式は実装時に実測・検証する。50 GiBだけで全処理の容量を保証しない。
DB・Docker等が使う/varの容量監視は別途維持し、Git保存先変更を理由に省略しない。

### 最終作業による利用状況

初期のrepo保守は、最終作業日時と期間nからの利用状況判定に限定する。nの初期値は90日とする。
作業実績として記録するのは、ref更新が成功したpushとrepo固有設定の変更成功だけとする。
clone・fetch、監視、バックアップ、復元検証、清掃、失敗操作は作業日時を更新しない。
Git取得の最終アクセス日時は別目的で記録可能だが、利用状況の判定には使用しない。

| usage status | 表示 | 判定 |
| --- | --- | --- |
| recently_used | 最近利用あり | 対象となる作業実績があり、最終作業からn日未満 |
| inactive | 長期間利用なし | 対象となる最終作業からn日以上経過 |
| never_used | 利用実績なし | 対象となる作業実績がない |

作成だけでは作業実績にせず、最初の対象操作までnever_usedとする。n日ちょうどはinactiveと判定する。
既存repoの作業日時を監査等で復元できない場合、アクセス日時から推測せず、移行時の扱いを確認する。
usage statusはlifecycle・healthとは別属性とし、inactiveだけで無効化・削除・アーカイブ・GCを行わない。
状態によってバックアップ対象から除外しない。容量・破損の点検や取得時の排他・整合性確保も維持する。
共通設定でnを変更した場合は利用状況を再評価するが、repoの最終作業日時そのものは更新しない。

### 受信・点検・保守

制限項目・標準動作はGitLab Self-Managedを基本に整理する。GitLab.comのサービス固有上限とは区別する。
[GitLabの容量設定](https://docs.gitlab.com/administration/settings/account_and_limit_settings/)ではrepo容量の0は制限なし、
[アプリケーション制限](https://docs.gitlab.com/administration/instance_limits/#max-push-size)では最大pushサイズは標準未設定とされる。
これらは参照基準であり、現行GitLabの実設定を取得した結果やMomiServerの全上限を無制限に確定した記録ではない。
MomiServerにはGitalyがないため、Gitaly内部のRPC時間上限等をそのままGit HTTP全体へ流用しない。
MomiServerの初期値は前節で確定した安全上限を使用する。GitLabの設定を自動取得・反映する機能ではない。

- 論理容量の上限、受信pack上限、object上限、同時受信数・予約容量、空き容量下限を個別に設定する。
- 履歴込みのrepo・サービス全体の実使用量を監視し、初期制限値と共通設定による警告・停止条件を適用する。
- 複数repoの受信が空き容量を同時消費するため、容量予約はサービス全体でも管理する。
- 受信中・ref更新前にも再確認し、不足ならrefを変更しない。低容量時に自動pruneで対処しない。
- 拒否packの一時データ・到達不能objectが残る可能性を容量へ含め、猶予付き保守で扱う。
- 起動時と既定60秒の軽量点検で配置、HEAD、状態、容量、監視最終成功を確認する。
- 全objectの重いfsckは毎60秒行わず、復元時・異常時・別の保守予定に分離する。
- GC・repack・prune等の実行機能は将来対応とし、初期の保守では自動実行しない。
- 将来の清掃・物理削除でもpush・復元・バックアップとの排他と、猶予・バックアップ・承認条件を要求する。
- 合意した初期値の実装・境界試験と、[設計全体の残件](./000_index.md)の解消を導入前に行う。

## エラー方針

認証・認可のHTTP区分は認証設計に従う。容量は受信前なら413等、サービス停止・DB障害は503で区別する。
Gitプロトコル開始後はGitのunpack/ref結果で失敗を返す場合があり、HTTP 200だけで成功判定しない。
詳細原因はSecret・物理パスを除いた監査へ記録し、外部へは安定したエラー分類を返す。

## 実装時の受入条件

| ID | 確認内容 |
| --- | --- |
| GS-01 | 作成の各段階を中断し、IDとHEADを維持して再開・隔離できる |
| GS-02 | rename・所属変更で保存先不変。リンク、外部alternates、不正URLは拒否 |
| GS-03 | 同時push、同時削除、atomicの競合、中断で既存refを破損しない |
| GS-04 | ref確定後のDB障害・再起動から実行者付き監査を一度だけ補完できる |
| GS-05 | pack・object・複数受信の容量超過、OS書込失敗、部分更新疑義で安全に停止する |
| GS-06 | 30日削除猶予、90日作業判定とclone/fetch除外、共通設定、状態だけで自動清掃しないことを確認 |

将来の清掃機能では90日復旧猶予・reflog保護・GC排他も別途検証する。既存の点検・監査補完の安全条件は維持する。
