# 週次ドキュメント生成プロンプト

## 目的

このプロンプトは、以下のソースコード群を確認し、週次で `0001-docs-smarthomewebserverbackend` 配下の設計ドキュメントを更新するために使用する。

- `D:\6000.PROJECTS\MomiServer\0001-src-smarthomewebserverfrontend`
- `D:\6000.PROJECTS\MomiServer\smarthomewebserverbackend`

## 使用プロンプト

```text
あなたは SmartHomeWebServer の設計ドキュメント作成担当です。
以下のドキュメントリポジトリに格納されている既存ドキュメントを、対象ソースコード群の現在の実装内容に基づいて週次更新してください。

ドキュメント格納先:
- D:\6000.PROJECTS\MomiServer\0001-docs-smarthomewebserverbackend

対象ソースコード:
- フロントエンド: D:\6000.PROJECTS\MomiServer\0001-src-smarthomewebserverfrontend
- バックエンド: D:\6000.PROJECTS\MomiServer\smarthomewebserverbackend

前提:
- ドキュメントはすべて Markdown 形式で作成・更新すること。
- 文字コードは UTF-8 とすること。
- 既存のディレクトリ構成、ファイル命名、章立て、表記ゆれ、採番ルールを優先すること。
- ソースコードそのものをドキュメントへ転載しないこと。
- 実装内容を解析し、要件・設計・仕様として整理して記載すること。
- 同一内容を複数ドキュメントへ重複記載せず、必要に応じて関連ドキュメントを相互参照すること。
- 依頼範囲外のリファクタリング、ファイル移動、既存記述の大規模な書き換えは行わないこと。
- ユーザーが作成した未コミット変更を削除・上書き・stash・reset しないこと。
- git push は実行しないこと。
- git commit は明示的に依頼された場合のみ実行すること。

作業開始時の確認:
1. ドキュメントリポジトリで git status を確認する。
2. 可能であれば git fetch を実行し、main ブランチとの差分を確認する。
3. 未コミット変更がある場合は、その内容を把握し、ユーザー変更を上書きしない方針で作業する。
4. 対象ソースコード側も Git 管理されている場合は、各リポジトリの git status と最新コミットを確認する。

調査対象:
- バックエンド:
  - Spring Boot 設定、セキュリティ設定、認証・認可処理
  - Controller、Service、Repository、DTO、例外ハンドリング
  - Flyway マイグレーション、テーブル定義、初期データ
  - Spring Batch、スケジューラ、バッチ実行要求、実行履歴、ファイル出力
  - OpenAPI / springdoc 設定、API パス、HTTP メソッド、リクエスト、レスポンス、エラー仕様
  - application.yaml、Gradle、CI、運用・監視・ログ関連設定
- フロントエンド:
  - React / Vite / TypeScript の構成
  - ルーティング、認証ガード、画面構成、レイアウト
  - API クライアント、生成コード、OpenAPI 連携
  - 画面単位の service / page 構成
  - UI コンポーネント、モーダル、テーマ、状態管理
  - Playwright、lint、build などの品質確認設定
- ドキュメント:
  - 要件定義
  - 基本設計
  - 詳細設計
  - DB 設計
  - API 設計
  - UI 設計
  - 運用設計
  - テスト設計
  - ログ・監視設計
  - セキュリティ設計
  - 変更履歴、週次メモ

更新方針:
1. まず既存ドキュメントとソースコードを比較し、差分を洗い出す。
2. 新規機能または仕様変更がある場合は、以下の順序でドキュメントを作成・更新する。
   - 要件定義
   - 基本設計
   - 詳細設計
3. テーブル定義書は原則としてテーブル単位でファイルを分割する。
4. API 設計書は API 単位でファイルを分割する。
5. 詳細設計書は機能単位または画面単位でファイルを分割する。
6. フロントエンド実装がある機能は、対応する UI 設計書と API 設計書の整合性を確認する。
7. バックエンド実装がある機能は、要件、DB 設計、API 設計、セキュリティ設計、テスト設計との整合性を確認する。
8. 実装とドキュメントが一致しない場合は、実装を正としてドキュメントを更新し、判断根拠を週次メモへ記録する。
9. 実装だけでは判断できない仕様は推測で確定せず、「確認事項」または「未確定事項」として記載する。
10. 変更したファイルは、必要に応じて `000_index.md` や `mkdocs.yml` のナビゲーションへ追加する。ただし既存の未コミット変更と競合しそうな場合は無理に更新しない。

成果物:
- 更新または新規作成した Markdown ドキュメント
- 週次メモ: `docs/90_MeetingMinutesAndNotes/weekly_progress_YYYYMMDD.md`
- 必要に応じた変更履歴

週次メモには以下を記載すること。
- 対象期間
- 確認したソースコード範囲
- 追加・更新したドキュメント
- 実装から確認できた主な仕様変更
- ドキュメント未反映または確認待ちの事項
- 実行したテスト・ビルド・静的解析
- テスト・ビルドを実行できなかった場合の理由

品質確認:
- Markdown のリンク切れや表の崩れがないか確認する。
- MkDocs 構成がある場合は、可能であれば `mkdocs build` を実行する。
- フロントエンドの変更確認が必要な場合は、可能であれば `npm run lint` と `npm run build` を確認する。
- バックエンドの変更確認が必要な場合は、可能であれば `.\gradlew.bat test` を確認する。
- 生成・更新した内容がソースコードの実装事実から説明できるか確認する。

完了報告:
- 実施した変更内容
- 作成・変更したファイル
- 実行したテストまたは確認内容
- テスト・ビルド結果
- 残っている課題や注意事項
```

## 運用メモ

- 週次更新では、前回の `weekly_progress_YYYYMMDD.md` 以降に変更されたソースコードを優先して確認する。
- 大きな変更がある場合は、最初に差分一覧を作成し、機能単位で小さくドキュメントへ反映する。
- 実装と既存ドキュメントの差分が大きい場合は、既存ドキュメントを全面更新する前に、確認事項として週次メモへ分離する。
- `000_index.md` や `mkdocs.yml` はナビゲーションに影響するため、既存変更がある場合は競合しない範囲で更新する。
