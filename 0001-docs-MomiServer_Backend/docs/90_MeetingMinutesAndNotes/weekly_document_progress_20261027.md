## 決定事項

- 初期構成、バックアップ、保持削除、自動起動・更新、TLS・秘密情報、監視の条件を合意した。
- 一時ファイルの保持は当初の2週間案から最終回答の24時間へ変更した。
- 外部保存先未準備のリスクを了承するが、初期のバックアップ取得・復元確認は必須のままとする。
- 詳細復旧手順等を後続へ分離し、本番受入タスクは完了にせず「対応中」とした。
- 追加確認により、本番は未導入・未運用で、完成後に導入する予定と明記した。
  開発端末での起動・検証と本番運用を区別する。
- ソースコードを今後GitHubにも保管し、バックアップを兼ねる予定を追記した。
  運用データのバックアップとは分離し、実際の障害対応手順は今後の検討事項として残す。
- 追加回答でFE・BEの直接実行、専用ユーザー、Webホスト名、VPNの接続境界を確定した。
  VPNでのWeb操作も通常のロールに従い、閲覧専用にはしない。
- バックアップは週次差分・月次フルへ、許容データ損失は最大1週間へ変更した。
  旧案の毎日01:00・成功14世代は撤回し、実行日時・保持世代・差分比較基準は具体化時の確認事項とする。
- Raspberry Piの監視はサーバー稼働・証明書期限に絞り、容量管理はMomiServer側、バックアップは専用スクリプトとした。
- 導入版の追跡、更新時のバッチ完了待ち・未送信結果保持、DB移行失敗時の直前バックアップ復旧を追記した。
- 通常は無効の緊急管理手段と、停止中通知の復帰後保存を方針として記録した。
  追加回答で、専用の緊急ADMINアカウント、新規開始・自動配信の一時停止、Agentとサーバー両方の通知を確定した。

詳細な値・適用範囲・例外は運用設計を参照し、本メモへ重複掲載しない。

| 区分 | 内容 |

## 課題・次回アクション

- 本番パス・systemd構成・バックアップ取得方式・復元方法を具体化する。
- 週次・月次の実行日時と保持世代、差分の比較基準・依存関係を具体化する。
- GitHubへのソース保管対象・方式と、障害時の切り分け・復旧・切戻しを別途検討する。
- ログ・通知の1年境界と対象対応、一般一時清掃、監視閾値を確定する。
- 証明書の発行・信頼配布、資格情報別の交換方式を設計する。
- 本番の構築・受入証跡を取得する。未確認を完了済みと扱わない。
- 確定した緊急ADMINの管理手順、保守モード、停止中通知の保持・遡及判定と重複防止を具体化する。
