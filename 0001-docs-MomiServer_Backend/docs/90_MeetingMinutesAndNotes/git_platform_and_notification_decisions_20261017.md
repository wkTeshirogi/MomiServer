# Git基盤内蔵化・Git専用通知 方針決定メモ 2026/10/17

## サマリ

MomiServerのGit基盤は、GitLabを恒久的な内部依存として残す方式ではなく、Gitリポジトリ管理、Git通信、CI/CD、GitHub連携およびバックアップをMomiServerへ段階的に内蔵する方針とする。

CI/CD設定はMomiServerの管理画面を正規の編集手段とし、リポジトリ作成時に主要言語、利用する検査、実行契機および定期実行の有無を選択できるようにする。画面入力はバージョン付きの構造化設定として保存し、Pipeline実行時には変更不能な実行スナップショットへ変換する。

既存のGitLab CI/CD定義は移行資産として解析・取り込みに利用する。ただし、GitLab CI形式のファイルをMomiServer運用後の正本にはせず、完全互換も初期目標としない。

Git関連のDiscord通知は、既存の監視・セキュリティ・業務通知とは通知設定および通知先を分離する。CI/CDの開始・正常終了・エラー終了と、`main`ブランチへのマージ完了を主な通知対象とする。

## 背景

- 現在はGitLab Self-ManagedをGitリポジトリおよびCI/CDの実行環境として使用している。
- GitLabをバックグラウンドサービスとして維持し、MomiServerから管理する案も検討した。
- 最終的にはGitサーバ機能全体をMomiServerへ内蔵し、GitLabの運用・更新に依存しない構成を目指す。
- GitHubはGitリポジトリの正本にはせず、非公開バックアップ、公開ミラーまたはRelease公開先として使用する。
- 現在のDiscord通知は監視、セキュリティおよび業務イベントを対象としているため、Git開発イベントを同じ通知経路へ混在させると、通知量、通知先および障害影響の境界が不明確になる。

## Git基盤の責務

MomiServerへ内蔵するGit基盤は、少なくとも以下の責務を持つ。

| 区分 | 責務 |
| --- | --- |
| リポジトリ管理 | 作成、更新、論理削除、復元、容量取得、バックアップ |
| Git通信 | HTTPSによるclone、fetch、pull、push |
| 認証 | Gitクライアント向けPersonal Access Tokenの発行、検証、失効 |
| 認可 | リポジトリ単位の参照、更新、管理権限の判定 |
| 参照管理 | branch、tag、commitおよびref更新履歴の管理 |
| 保護 | protected branch、force push、削除およびtag上書きの制御 |
| 監査 | 誰が、いつ、どのリポジトリとrefを操作したかの記録 |
| CI/CD | push等を契機としたPipeline生成、Job管理および結果保存 |
| Agent連携 | Job割当、ログ受信、キャンセル、ArtifactおよびCache管理 |
| GitHub連携 | 非公開バックアップ、公開ミラー、Release公開、同期照合 |

## CI/CD設定管理方針

### 設定の正本

CI/CD設定の正本はMomiServerが保持するバージョン付き構造化データとし、管理画面を正規の編集手段とする。リポジトリ内の設定ファイルを直接解釈して自動的にサーバ設定を変更する方式は採用しない。

設定変更時には、変更前後の差分、変更者、変更日時および変更理由を記録する。Pipeline開始時には、使用するCI/CD設定、言語テンプレートのバージョン、実行コンポーネントのバージョンおよびSecret参照を実行スナップショットとして確定する。後から設定が変更されても、過去のPipelineがどの条件で実行されたかを再現できるようにする。

画面管理によって可搬性が失われないよう、機密値を除いた設定のエクスポート、インポートおよび差分確認機能を将来対象とする。エクスポート形式はバックアップおよび監査用であり、通常運用時の編集経路にはしない。

### リポジトリ作成時の設定

リポジトリ作成画面では、少なくとも以下を設定する。

| 項目 | 内容 |
| --- | --- |
| 主要言語 | Java、JavaScript／TypeScript、Go、Python、ドキュメント等から選択する |
| ビルド方式 | Gradle、Maven、npm、pnpm、Go Modules等を主要言語に応じて候補表示する |
| 言語・ツールバージョン | JDK、Node.js、Go等の実行バージョンを選択する |
| CI/CDテンプレート | 主要言語とビルド方式に対応する推奨テンプレートを選択する |
| 通常チェック | ビルド、単体テスト、Lint、静的解析等の初期有効・無効を選択する |
| 定期チェック | 定期検査全体の有効・無効と推奨セットを選択する |
| 実行環境 | 必要なAgent能力、コンテナイメージ、CPU、メモリおよびタイムアウトの既定値を選択する |
| 通知 | 失敗、復旧、`main`成功等のGit専用通知条件を選択する |

初期段階では主要言語を1つ選択する。複数言語を含むリポジトリへの対応は必要性を確認して別途要件化し、補助言語または複数プロジェクトルートを登録できる構造を検討する。

主要言語はテンプレート選択の起点として利用するが、拡張子だけで実行内容を確定しない。既存リポジトリの取り込み時には構成を検出して候補を提示し、利用者の確認後に設定を保存する。

### CI/CD項目ごとの画面設定

管理画面では、Pipeline定義ファイルを直接編集させず、以下の機能を項目単位で有効化および設定できるようにする。

| 分類 | 項目例 | 主な実行契機 |
| --- | --- | --- |
| ビルド | コンパイル、成果物生成 | MR、push、`main`へのマージ後 |
| テスト | 単体テスト、結合テスト | MR、push、手動 |
| コード品質 | Lint、SpotBugs、SonarQube | MR、`main`へのマージ後、定期 |
| セキュリティ | FindSecBugs、依存関係、Secret、コンテナ検査 | MR、依存関係変更時、定期 |
| サプライチェーン | SBOM生成、ライセンス検査、署名 | `main`、Release、定期 |
| 配布 | Package、Container Image、Release成果物 | tag、Release、手動承認後 |

各項目では、少なくとも以下を設定できるようにする。

- 有効・無効
- 実行契機
- 対象branch、tagおよび変更パス
- 使用するテンプレートまたは実行コンポーネントのバージョン
- 実行環境と必要なAgent能力
- タイムアウト、再試行および同時実行数
- 成功・失敗の判定基準
- Artifact、レポートおよびログの保持期間
- Pipelineを失敗させるか、警告として継続するか
- Git専用Discord通知の対象とするか

任意コマンド入力は、標準テンプレートで対応できない場合の拡張機能として扱う。導入する場合も権限制御、承認、監査および分離実行を必須とし、リポジトリ作成時の標準設定には含めない。

### 定期チェック

定期チェックの有効・無効はリポジトリ作成時に選択でき、作成後もCI/CD設定画面から変更できるようにする。単一の全体スイッチだけではなく、チェック項目ごとに周期を設定可能とする。

| 設定項目 | 内容 |
| --- | --- |
| 有効・無効 | 定期チェック全体および個別項目の実行可否 |
| 周期 | 日次、週次、月次または個別スケジュール |
| 実行日時 | 曜日、時刻およびタイムゾーン |
| 対象ref | 原則として既定branchの最新commit |
| 重複時動作 | 前回実行を待つ、今回をスキップする、前回を中止する |
| 未実行時動作 | サーバ停止等で逃した実行を再開後に補完するか |
| 結果判定 | Pipeline失敗、警告または記録のみ |
| 結果通知 | 新規検出、悪化、復旧、実行エラー等の通知条件 |
| 結果集約 | 専用ページ、Issue、Artifactまたはレポート履歴への反映 |

初期テンプレートでは、SpotBugsおよびFindSecBugsをMR時、SonarQubeを`main`へのマージ後、Dependency-Checkを依存関係変更時および週次の定期チェックとする案を既定値とする。ただし、ツール名をPipelineの制御単位にはせず、コード品質、静的セキュリティ解析、依存関係検査等の検査種別として管理する。

定期チェックの結果は実行成否と検査結果を分離する。検査ツール自体の異常終了、脆弱性・品質問題の検出、前回から変化がない状態を区別し、同一内容を毎回通知しない。

### テンプレートと設定継承

CI/CDテンプレートは、主要言語、ビルド方式および用途ごとにMomiServerが管理する。テンプレートには推奨チェック、実行順序、実行環境、キャッシュ、レポート形式および既定の判定基準を含める。

設定はシステム、グループおよびリポジトリの順に継承できるようにする。リポジトリ画面では、各値がテンプレート、グループ既定値またはリポジトリ上書きのどこから適用されたかを表示する。

テンプレート更新時は既存設定を自動上書きせず、影響、差分および移行可否を表示する。セキュリティ上の緊急更新を強制適用する仕組みを設ける場合は、対象範囲、猶予期間、例外承認および監査を別途設計する。

### GitLab CIからの移行

初期実装では、現在のMomiServer関連リポジトリで使用している`.gitlab-ci.yml`を調査し、画面設定へ変換可能な要素と個別対応が必要な要素を分類する。

移行機能はGitLab CI定義を直接実行する互換エンジンではなく、解析結果をMomiServerのCI/CD項目へ対応付けるインポート支援として実装する。対応できない条件、独自スクリプトおよび外部サービス依存は警告として表示し、利用者が変換結果を確認してから保存する。

GitLab固有変数は必要に応じて移行候補へ対応付けるが、MomiServer上のSecretまたは実行コンテキストへ無条件にコピーしない。

## GitHub連携先設定

### 設定単位

GitHub連携先は、以下の単位で設定できるようにする。

| 設定単位 | 用途 |
| --- | --- |
| システム | GitHub連携全体の既定値。未設定も許容する |
| グループ | グループ配下のリポジトリに適用する既定値 |
| リポジトリ | 特定リポジトリだけに適用する上書き値 |

有効な設定は、リポジトリ、最も近い親グループ、上位グループ、システムの順に解決する。上位設定を継承するか、連携を無効化するか、別の連携先へ上書きするかを明示的に選択できるようにする。

管理画面では設定値だけでなく、継承を解決した後の有効値と、その値がどの階層で設定されたかを表示する。

### 連携用途

リポジトリは、用途ごとに複数のGitHub連携先を持てるようにする。

| 用途 | 想定Visibility | 同期内容 |
| --- | --- | --- |
| 非公開バックアップ | private | 許可した全branch、tagおよびGit履歴 |
| 公開ミラー | public | 公開を許可したbranch、tagおよびGit履歴 |
| Release公開 | publicまたはprivate | Release成果物、チェックサム、リリースノート |

非公開バックアップと公開ミラーを同じGitHubリポジトリへ切り替えて使用する運用は原則として採用しない。公開範囲の誤設定を防ぐため、用途ごとに別の連携設定と監査記録を持つ。

### GitHubパスの表現

GitHub上のリポジトリは、自由入力されたURL文字列ではなく、以下の構造で管理する。

- GitHub接続先ID
- GitHub Owner種別
- GitHub Owner名
- GitHubリポジトリ名
- 用途
- Visibility
- 同期対象ref
- 有効・無効

GitHubにはMomiServerのグループ階層をそのまま格納するリポジトリパスがないため、グループ設定ではGitHubリポジトリ名の生成規則を指定できるようにする。

生成規則の候補は以下とする。

- リポジトリ名をそのまま使用する
- グループ名を接頭辞として付与する
- MomiServer上のグループパスを区切り文字で連結する
- リポジトリ単位で固定名を指定する

生成後のGitHub Owner名とリポジトリ名の組み合わせが重複する場合は、作成または設定保存を拒否し、明示的な上書きを要求する。

### 設定項目案

| 項目 | 内容 |
| --- | --- |
| 連携用途 | 非公開バックアップ、公開ミラー、Release公開 |
| 継承方式 | 親設定を継承、無効化、個別設定 |
| GitHub接続先 | GitHub Appのインストール先を参照するID |
| GitHub Owner | UserまたはOrganizationの名前 |
| リポジトリ名規則 | グループ既定の名前生成規則 |
| 固定リポジトリ名 | リポジトリ単位の明示的な名前 |
| Visibility | privateまたはpublic |
| 同期対象 | 全ref、protected branch、指定branch、tag |
| 同期契機 | push後、Release作成後、定期照合、手動実行 |
| 自動作成 | GitHub側に対象がない場合の自動作成可否 |
| 公開前検査 | Secret、内部情報、ライセンスおよび履歴の検査 |
| 不一致時動作 | 自動上書き、停止、管理者承認待ち |

GitHubの認証情報そのものをグループまたはリポジトリ設定へ保存せず、別途安全に管理するGitHub接続先をIDで参照する。GitHub Appを第一候補とし、個人のPersonal Access Tokenへの恒常的な依存を避ける。

### 設定変更時の扱い

GitHub Owner、リポジトリ名または用途を変更しても、既存GitHubリポジトリの移動、名前変更または削除は自動実行しない。変更後の連携先を検証し、初回同期の影響を表示した上で、管理者の承認後に切り替える。

連携解除時もGitHubリポジトリは自動削除せず、MomiServerからの同期だけを停止する。GitHub側の削除は独立した高リスク操作として扱う。

## Git専用Discord通知

### 分離方針

Git専用Discord通知は、既存の監視・セキュリティ・業務通知とは以下を分離する。

- 有効・無効設定
- Webhook URL
- 通知先チャンネル
- イベント種別
- メッセージテンプレート
- 再試行状態
- 通知履歴
- レート制御

Discord WebhookへHTTPリクエストを送信する低レベル処理は共通部品として再利用可能とするが、Gitイベントの判定、メッセージ生成、通知先解決および配信状態管理はGit通知機能の責務とする。

### 通知イベント案

| イベント種別 | 発生条件 | 通知タイミング | 初期重要度 |
| --- | --- | --- | --- |
| `git_pipeline_started` | CI/CD Pipelineの実行開始 | 実行状態を保存した後 | info |
| `git_pipeline_succeeded` | Pipelineが正常終了 | 最終結果を保存した後 | success |
| `git_pipeline_failed` | Job失敗等によりPipelineがエラー終了 | 最終結果と失敗Jobを保存した後 | error |
| `git_pipeline_cancelled` | 利用者またはシステムがPipelineを中止 | 最終結果を保存した後 | warning |
| `git_pipeline_timed_out` | PipelineまたはJobがタイムアウト | 最終結果を保存した後 | error |
| `git_main_merge_completed` | 変更がマージ操作によって`main`へ反映 | ref更新と監査記録の確定後 | success |

開始・正常終了通知をすべてのbranchで有効にすると通知量が増えるため、リポジトリ単位またはbranch単位で通知対象を設定できるようにする。エラー終了および`main`へのマージ完了は、初期状態で通知対象とする案を優先する。

### 通知内容案

通知には以下の情報を含める。

- リポジトリ名
- Pipelineまたはマージのイベント種別
- 実行状態
- 対象branchまたはtag
- 対象commitの短縮SHA
- 起動者またはマージ実行者
- 開始日時および終了日時
- 実行時間
- 失敗したJob名と要約
- MomiServer上のPipeline、commitまたはマージ結果へのリンク

通知本文には、Personal Access Token、CI/CD Secret、Webhook URL、環境変数の機密値、Jobログ全文を含めない。エラー内容は調査開始に必要な要約に限定し、詳細ログはMomiServer上で認証後に参照する。

### 配信制御案

- Gitイベントと通知イベントを同一トランザクションまたはOutbox方式で対応付ける。
- 通知イベントごとに一意なIDを付け、再送時の重複を識別できるようにする。
- Discord送信は非同期処理とし、Pipelineやマージ処理を待機させない。
- 一時的な送信失敗は再試行し、上限到達後は失敗状態として保持する。
- Webhookの無効化、認証失敗およびDiscord側レート制限を区別して記録する。
- 同一Pipelineについて、終端状態の通知を複数回送らない。
- 通知の有効・無効、送信先変更および手動再送を監査ログへ記録する。

## フェーズ共通の実装原則

- 各フェーズで要件定義、基本設計、詳細設計、実装、テストおよび運用確認の順序を守る。
- Gitリポジトリ、CI/CDおよびSecretを扱う機能は、正常系だけでなく権限違反、異常切断、再試行、同時実行および復旧を確認する。

- フェーズ完了時にはバックアップと復元を含む検証証跡を残す。

| Git基盤実装方式 | 隔離技術検証済み | 2026/10/29にJGit 7.8でWindows・Linux各17件成功。次の基本設計へ進む採用候補。本番への正式採用は結合確認後 |
| Phase 0要件範囲 | 確定 | FR-0054からFR-0056へリポジトリ管理、HTTPS Git通信、認証・認可、ref保護、監査、バックアップ・復旧および初期対象外を反映 |

| 実装・テスト | 技術検証のみ実施 | 独立した試験コードを追加。本番Git機能・実DB・既存SecurityConfigとの統合は未実施 |

### 2026/10/29 基本設計の追加合意

- システムADMINは全repoを管理可能とする。他の通常ロールはgroup・repoで明示付与し、未付与は拒否する。
- mainへの通常の直接pushは禁止し、初回作成・障害復旧だけ管理者の明示操作で例外許可する。
- バックアップ復元後はGit PATをすべて失効し、再発行する。
- Git PATの初期値・最大期間は1年、無期限なしとする。週次差分は直近月次フル基準とし、DBは週次も完全取得する。
- 通常の履歴保持と容量管理を分離する。保持対象・清掃条件・指標の正本は
  [ストレージ基本設計](../02_SystemDesign/Git基盤/0001_storage.md)とし、猶予・制限値の最新合意状況も同書で管理する。
- 制限設計はGitLab Self-Managedを基本とする。サービス固有値やGitaly内部制限を無条件に流用しない。
- 週次差分は月曜03:00、月次フルは毎月1日03:00、日本時間で開始する。重複日は週次を中止し月次のみ実行する。
- Git制限値は共通設定で変更可能とする。repo保守は当面、成功push・設定変更からの利用状況判定のみとする。
- clone・fetchは作業判定から除外する。90日判定、30日削除猶予、90日復旧猶予、バックアップ3/8世代等を合意した。
- 詳細値・除外条件・依存世代の保護は基本設計を正本とする。自動GC・prune・物理削除は当面実施しない。
- 導入予定機の/var空き15G・/opt空き1.7Tを踏まえ、Git・作業・暫定バックアップは/opt側の正式パスへ配置する。
- 初期制限値、BE停止目標30分、60分後の最大2回再試行、復帰後1回の補完を合意した。詳細は領域設計を正本とする。
- 既存Certbot更新設定はLet’s Encrypt本番接続とnginxプラグインであることをユーザー提示値から確認した。
- 既存方式の流用方針に対し、.localでは公開CAを利用できない制約を確認した。ホスト名・CA方式は追加判断待ちとする。
- 追加合意でVPNなし公開をWebと必要なAPI・WebSocketに限定した。Git通信はLAN／VPN内のままとする。
- 検索非掲載はnoindex、データ保護は認証・認可で分離する。具体DNS名・TLS検証方式・公開経路は追加確認する。
- ホスト名変更・プライベートCA追加・検証用ポート公開等の本番設定は、設計上の合意だけで実施しない。
- 更新の稼働・反映・信頼配布、外部退避先・実機検証は残件とする。
- Git基本設計の導入条件・未決定値の確定タスクは完了とする。DNS・証明書・公開経路等の具体化を完了条件に加えない。
- 上記の運用具体化は既存の本番導入・運用受入へ集約し、合意した公開境界・検索非掲載等の安全方針は維持する。
- Git機能はMomiServer本体へ含めるとユーザーが再確認した。独立JGit検証と本番のFE・BE内蔵を明確に区別する。
- 継承解決、操作予定による監査補完、停止取得、差分方式等の設計判断と未決定事項は基本設計を正本とする。
- 一般Web画面のロール制御や外部在庫APIキーの仕様は変更しない。Git基盤MVPの実装完了とは扱わない。
