# 一覧ページング共通設計

## 概要

独立した検索・一覧画面で一度に表示するデータ件数とページ移動操作を統一する。
大量データによる画面の縦長化を抑え、画面ごとに異なっていた件数表示と移動操作を共通部品へ集約する。

## 共通仕様

| 項目 | 仕様 |
| --- | --- |
| 初期表示件数 | 20件 |
| 選択可能件数 | 20件、50件、100件 |
| 件数変更 | 一覧ヘッダーの上にselectを配置し、変更時は先頭ページへ戻る |
| ページ移動 | 一覧の下に「前へ」「次へ」ボタンを配置する |
| 件数表示 | 一覧ヘッダーの上に現在の表示範囲、検索結果件数、必要に応じて全件数を表示する |
| 取得中 | 件数選択とページ移動を無効化 |
| 0件 | 表示範囲を0-0件とし、前後移動を無効化 |

## 実装方式

| 方式 | 適用条件 | 処理 |
| --- | --- | --- |
| クライアントページング | 一覧APIが対象データを一括取得する画面 | 共通フックで取得済み配列を20・50・100件に分割する |
| 段階取得後のクライアントページング | アラート | 既存配列レスポンスを維持し、offsetを使って100件単位で全件取得してから分割する |
| サーバーページング | APIログ、バッチ実行ログ | 選択件数をlimit、ページ位置をoffsetへ反映して再取得する |

上部の件数・selectは`ListPaginationSummary`、下部の前後移動は`ListPagination`、
クライアント側の状態管理と配列切り出しは`useListPagination`へ分離する。
画面固有の検索、並び順、更新処理は共通部品へ含めない。

## 適用画面

| 分類 | 画面 |
| --- | --- |
| 運用 | アラート、APIログ、在庫管理一覧、車両管理一覧 |
| マスタ | ユーザー、サービス、端末、品目、バッチ定義、バッチスケジュール、通知ルート設定、外部APIキー管理 |
| モーダル | バッチスケジュール実行ログ |

## 対象外

| 画面・領域 | 理由 |
| --- | --- |
| トップ画面の通知一覧 | ダイジェストとして最大5件を表示する個別要件を優先する |
| マシン・サービスステータス | 選択対象の状態監視画面であり、独立した検索一覧ではない |
| マスタ一覧・共通設定一覧 | 各機能へのメニューであり、業務データ一覧ではない |
| 詳細画面内の添付・通知設定等 | 親データに従属する編集領域であり、現時点では大量表示を想定しない |

## API連携

サーバーページングでは、画面で選択した20・50・100を`limit`へ設定する。
APIは要求件数より1件多く検索し、次ページの有無を`has_more`、検索条件に一致する総件数を
`total_count`で返す。
検索条件または表示件数を変更した場合は`offset = 0`として再取得する。

アラート取得APIは既存クライアントとの互換性のため配列レスポンスを維持する。
一覧画面は`GET /api/notifications/page`で`limit = 100`と、応答の`next_cursor`を使って段階取得する。
応答は`items`と`next_cursor`。継続位置がnullになるまで取得し、途中の新着は次回の再読込で取り込む。
カーソルは初回の最大行IDと、最後の作成日時・行IDを保持する。日時降順・ID降順、可視権限・期限・非表示除外を維持する。
追加でoffsetがずれたり、取得済み行の削除で後続が欠落したりすることを防ぐ。厳密なDB全体のスナップショットとは区別する。
再取得・画面遷移では共通非同期取得基盤で古い要求を中断し、古い応答が新しい結果を上書きしない。
トップ画面は従来どおり`limit = 5`のみを指定する。
APIログでは`total_count`に対して現在のoffsetが範囲外になった場合、先頭ページへ戻して再取得する。

### 表示件数と取得上限

| 対象 | APIの取得上限 | 画面の扱い |
| --- | --- | --- |
| クライアント方式の10画面 | 固定の上限なし。API応答を一括取得 | 取得後の配列を20・50・100件に分割 |
| アラート | 1要求は最大100件。取得合計の固定上限なし | 100件ずつ全件取得後に分割 |
| APIログ | 1要求は1から200件。省略時50件 | 画面は初期20件、最大100件を明示指定 |
| バッチ実行ログ | 1要求は20・50・100件のみ | 選択件数をそのまま指定 |

100件は全画面共通の取得上限ではない。
「全件数」はAPIの認可・状態等の条件を適用した件数であり、DB内の全レコード数とは限らない。
2026/10/24時点の差異と残対応は横断照合記録を参照する。
取得中と保存・更新中の操作制御を一律に変更する仕様は、本追記では確定しない。
