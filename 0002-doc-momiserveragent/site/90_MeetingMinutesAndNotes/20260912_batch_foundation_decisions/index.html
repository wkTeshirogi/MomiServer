    バッチ基盤の実行制御・連携方針¶

    概要¶

    サーバーとエージェント間の共通設定、開始待ち、結果確認、キャンセルの仕様を記録する。 本記録は会話で合意した設計方針であり、実装完了を示すものではない。 既存詳細設計と異なる部分は本記録を優先し、実装時にAPI・DB・画面へ反映する。

    日付¶

    • 判断日: 2026/09/12
    • 更新日: 2026/09/12

    背景¶

    エージェント側の既存設計を基準に、サーバー側のバッチ基盤と責務を整合させる。 結果未確認時は実行ステータスを維持するというユーザー方針を採用した。

    前提・制約¶

    • サーバーは共通設定、実行要求、結果確認、再実行判断を管理する。
    • エージェントは実行数制御、実行・停止、重複防止、結果の保存・再送を担当する。
    • 同じ実行IDの要求を再受信しても再実行しない。再実行には新しい実行IDを発行する。
    • 結果の再送とバッチの再実行を区別する。
    • API・DBの状態コードは英語、画面表示は日本語とする。

    判断¶

    結果未確認の扱い¶

    • 結果待ち期限を超えても running を維持し、画面では「実行中・結果未確認」と表示して通知する。
    • 期限到達だけで失敗、停止、キャンセル完了とは判定せず、自動再実行しない。
    • 遅れて確定結果が届いた場合は、元の実行IDに反映する。
    • 実行ステータスとは別に結果確認状況を保持する。unknown などの実行状態は追加しない。
    • 旧設計の「結果不明へ状態変更する」というサーバー側の扱いを、本方針へ変更する。
    • エージェントが成否を確認できない場合も、成功・失敗を推測して返さない。

    共通設定の初期値¶

    設定 初期値・起点
    同時実行数 エージェント1台あたり3件。結果送信待ちは含めない
    標準実行タイムアウト 実行開始から30分
    結果再送間隔 送信失敗から5分
    結果再送回数 初回を除き5回、最大6回送信
    未送信結果保持期間 ローカル保存から7日間。再送で延長しない
    サーバー結果待ち期限 最初の開始通知受信から1時間。重複通知で延長しない
    開始待ち期限 実行要求作成から1時間
    キャンセル停止猶予 通常停止要求から30秒

    設定の配布と適用¶

    項目 仕様
    配布 エージェント認証付きの共通設定取得API
    取得時点 起動時、再接続時、5分ごと
    識別 設定バージョンを付与
    通信断 最後に取得・保存した設定を使用
    初回取得前 新規実行を開始せず、取得まで待機
    タイムアウト優先順位 バッチ定義の個別指定、未指定なら共通設定
    要求単位の設定 タイムアウト・結果再送条件を要求作成時に確定・保存し、要求とともに配信
    実行中の変更 開始時に適用していた設定を維持
    同時実行数の変更 次の開始判定から適用。上限低下で実行中の処理を停止しない

    結果待ち期限は、個別指定を含む実行タイムアウトより長くなるよう検証する。 初期値の実行30分と再送待機25分は目安であり、停止・通信時間を含めた到着保証ではない。

    開始待ちと照合¶

    • 開始期限を実行要求に含める。開始待ち期限は共通設定で変更可能とする。
    • エージェントは期限切れの未開始要求を実行せず、期限切れを通知する。
    • サーバーで未配信のまま期限切れになった要求は expired に更新する。
    • 配信後に開始を確認できない場合は dispatched を維持し、「開始未確認」と表示して通知する。
    • 配信後の期限切れは、未開始であることをエージェントと照合してから確定する。
    • 開始通知は受理確認まで再送し、実際の開始日時を変更しない。
    • 再接続時は実行IDごとに受付・実行・結果の状態を照合する。

    キャンセル¶

    • 実行IDを指定する。未配信の要求はサーバーで cancelled に確定する。
    • 配信済み・実行中の要求はキャンセル要求を保存してエージェントへ配信する。
    • エージェントは通常停止を要求し、停止猶予後に強制終了する。子プロセスも停止対象とする。
    • 停止確認後に cancelled とする。停止未確認なら現在の状態を維持し、画面表示と通知を行う。
    • キャンセル要求中かどうかは、実行ステータスとは別に保持する。
    • キャンセルと処理完了が競合し、停止前に完了していた場合は実際の終了結果を採用する。

    状態コード¶

    コード 意味
    queued 配信待ち
    dispatched 配信済み、開始未確認
    running 実行開始済み、確定結果未受信
    success 正常終了
    failed 異常終了
    timeout 実行時間超過による停止をエージェントが確認
    cancelled キャンセル完了
    expired 未開始での期限切れを確認

    既存BEのコードを維持し、expired を追加する。 設計書中の Succeeded は success、Canceled は cancelled に対応する。

    判断理由¶

    • 通信断や通知欠落だけでは実際の実行状況を断定できないため、確認状況と実行状態を分ける。
    • 要求単位の設定を保存することで、実行条件の追跡と設定変更時の挙動を安定させる。
    • 開始期限と重複防止により、古い要求の遅延実行や二重実行を防ぐ。

    捨てた案と理由¶

    案 不採用理由
    結果待ち期限で実行状態を結果不明へ変更 実行中のまま維持するユーザー方針を採用
    結果未確認時に自動再実行 元の処理が動いている可能性があり、二重実行になる
    キャンセル送信時点で完了扱い 実際の停止を保証できない

    実装時の反映点¶

    • 共通設定の保存・配布APIと管理画面、実行要求への設定保存。
    • 結果確認状況、開始期限、キャンセル要求の管理項目。
    • expired のAPI・DB・画面対応と、サーバーのタイムアウト監視の修正。
    • 通知再送・照合・遅延結果受理の重複処理防止。
    • 通信断、開始通知欠落、設定変更、キャンセル競合を含む検証。

    具体的なAPIパス・ペイロード、開始通知再送の間隔、OS別停止方法は実装設計で具体化する。 これらの詳細値は今回の会話では合意していない。

    今後見直す条件¶

    • 長時間バッチ、通信断、処理集中で初期値が運用に合わない場合。
    • OSごとの停止能力や、再接続時の照合に制約が判明した場合。
