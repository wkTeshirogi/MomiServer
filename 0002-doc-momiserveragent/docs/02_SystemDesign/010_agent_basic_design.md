# エージェント基本設計

## 設計方針

もみサーバエージェントは、もみサーバからバッチ実行要求を受け取り、端末上で実行する常駐型ソフトウェアとして設計します。

エージェント本体は、バッチ実行要求受信、バッチ実行、実行結果収集、実行結果送信、端末状態記録、端末状態送信をPhase1の中心責務として持ちます。

エージェントは常駐アプリとして起動し、端末停止または明示的な停止指示までバックグラウンドで稼働します。常駐中は、バッチ実行要求の待受、端末状態の定期取得、送信失敗データの再送を継続します。

AI、MCP、Docker、Playwright、自己更新などの個別機能は、Phase1では対象外とし、将来拡張として扱います。

Windows、Linux、macOSは通常エージェントとして必須対応します。AndroidまたはiOSは、モバイルエージェントとしてどちらか一方に対応できればよい設計とします。

## 実装言語の決定

2026年9月12日の仕様検討により、Windows・Linux・macOS向け通常エージェント本体の実装言語にGo（Golang）を採用します。

### 採用理由

- Windows上で各OS向けの実行ファイルと配布アーカイブを作成し、配布作業を集約したいという運用要件を優先します。
- 要求受信、外部バッチ実行、端末情報収集、結果保存・再送を中心とする常駐エージェントとして構成します。
- エージェント本体用のJava実行環境を導入先で別途管理しない配布方式にします。

比較候補はGoとJavaでした。
Javaには既存バックエンドの言語・開発知識を活用できる利点があり、ランタイム同梱配布も可能です。
ただし、標準のjpackageによるOS固有パッケージの作成は対象OS上で行う必要があります。
今回のWindows中心の配布物作成方針にはGoが合うと判断しました。
これは今回の要件に基づく選択であり、Javaの運用・保守が一律に劣るという判断ではありません。

### 適用範囲と設計上の制約

採用対象は通常エージェント本体です。実行対象のバッチの言語と、将来のモバイルエージェントの言語は別途扱います。
バッチが必要とするシェルやランタイムは導入端末側で準備します。

通信、実行ID管理、結果保存・再送は共通処理とし、常駐サービス制御、権限、子プロセス停止、
OS固有の情報取得はOS別の処理として分離します。
将来のPluginは本体への組込みまたは別プロセス連携を候補とし、Windows非対応のGo標準pluginを前提にしません。

ビルド、依存ライブラリの選定条件、配布形式、対象OSでの検証は[インフラ設計](../03_InfrastructureDesign/000_index.md)を参照します。

| 種別 | 対象OS | 対応方針 | 主な機能 |

## 責務分担

| 領域 | 責務 |
| --- | --- |
| Web | エージェント状態、バッチ実行状態、端末状態を表示します。 |
| API | エージェント登録、認証、バッチ実行要求配信、結果受信、端末状態受信を提供します。 |
| Scheduler | バッチ実行タイミング、実行対象、再実行を管理します。 |
| 通常エージェント | PC/サーバ上でバッチ実行、実行結果送信、端末状態記録、端末状態送信を担当します。 |
| モバイルエージェント | モバイル端末上で端末情報送信、状態同期、通知、軽量処理を担当します。 |
| Database | エージェント情報、ジョブ情報、ログ、監視情報を保持します。 |

## エージェント内部構成

### 設定と実行判断の分担

実行環境は端末ごとのデフォルトと設定ファイルで管理します。
実行制御および結果送信の運用設定はサーバ側の共通設定として管理し、エージェントが適用します。
バッチ自体の再実行はサーバが判断し、エージェントによる結果再送とは区別します。

実行IDと処理状況、未送信結果は再起動後も確認できるように永続化します。
実行結果と送信状態を分離し、通信失敗によって判明済みの成功・失敗情報を失わない設計とします。

設定値は[実行制御詳細設計](Details/040_execution_control.md)、
実行環境と重複防止は[バッチ実行詳細設計](Details/030_job_execution.md)、
再送と結果照合は[ログ・結果通知詳細設計](Details/050_log_result_notification.md)を参照します。

### コンポーネント一覧

| コンポーネント | 役割 |
| --- | --- |
| Agent Core | 常駐処理、設定読込、ライフサイクル管理を担当します。 |
| Connection Manager | 認証、ハートビート、接続状態の管理を担当します。 |
| Batch Receiver | もみサーバからバッチ実行要求を取得します。 |
| Batch Execution Manager | バッチ実行、同時実行数、タイムアウトを制御します。 |
| Log Collector | stdout、stderr、ExitCode、実行時間を収集します。 |
| Device Status Recorder | CPU温度、CPU使用率、メモリ使用量、HDD/SSD容量などを記録します。 |
| Device Status Sender | 記録した端末状態をもみサーバへ送信します。 |
| Resident Service Controller | 常駐起動、停止指示、異常終了時の再起動方針を管理します。 |
| Mobile Adapter | モバイルOSの制約に合わせた同期、通知、軽量処理を担当します。 |
| Update Manager | 自己更新と再起動を制御します。Phase1では将来拡張扱いとします。 |

## Phase設計

| Phase | 目的 | 対象機能 |
| --- | --- | --- |
| Phase1 | 最小構成の常駐型バッチ実行・端末状態送信エージェントを実現します。 | 登録、認証、常駐稼働、稼働状態送信、バッチ実行要求受信、バッチ実行、実行結果送信、CPU温度、CPU使用率、Memory、HDD/SSD容量 |
| Phase2 | 管理エージェント機能と拡張実行方式を追加します。 | AndroidまたはiOS、Docker、PowerShell、Node.js、Playwright、MCP、AI、Temperature、Network、サービス状態取得 |
