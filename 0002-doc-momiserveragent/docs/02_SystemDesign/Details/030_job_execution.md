# バッチ実行詳細設計

> 2026/09/12更新: 状態コード・結果未確認の扱いは
> [バッチ基盤の合意記録](../../90_MeetingMinutesAndNotes/20260912_batch_foundation_decisions.md)を優先します。
> 以下には変更前の設計を含みます。合意は実装完了を意味しません。

## 目的

バックエンドから受信したバッチ実行要求を、導入端末上で実行します。

## Phase1対象範囲

| 種別 | 内容 | Phase |
| --- | --- | --- |
| Batch | バックエンドから通知されたバッチ実行要求を実行します。 | Phase1 |
| Docker | Dockerコンテナとして処理を実行します。 | Phase2 |
| PowerShell | PowerShellスクリプトを実行します。 | Phase2 |
| Node.js | Node.jsスクリプトを実行します。 | Phase2 |
| AI | AIを利用する処理を実行します。 | Phase2 |
| Playwright | ブラウザ自動操作処理を実行します。 | Phase2 |
| MCP | MCP連携処理を実行します。 | Phase2 |

## 実行フロー

実行環境と制御条件を確認し、実行前に実行IDと処理状況を永続化します。
同じ要求を同時に受信した場合も、同一実行IDについて実行を開始できる処理は一つに限定します。

```text
バッチ実行要求受信
  |
  | execution_id重複確認
  v
実行コマンド確認
  |
  | 作業ディレクトリ確認
  v
タイムアウト設定確認
  |
  | 開始通知
  v
バッチ実行
  |
  | ログ収集
  v
終了状態判定
  |
  | 実行結果送信
  v
バッチ完了
```

## バッチ状態

| 状態 | 内容 |
| --- | --- |
| Queued | 実行待ち状態です。 |
| Running | 実行中状態です。 |
| Succeeded | 正常終了状態です。 |
| Failed | 異常終了状態です。 |
| Timeout | タイムアウト終了状態です。 |
| Canceled | キャンセルされた状態です。 |
| 結果不明 | 再起動等により実際の成否を確認できない、またはサーバが期限内に結果を確認できない状態です。 |

結果不明は失敗やプロセス停止を意味しません。
送信失敗と結果不明の区別は[ログ・結果通知詳細設計](050_log_result_notification.md)を参照します。

## 実行環境

実行ユーザー、利用するシェル、作業ディレクトリにはデフォルトを設け、端末側の設定ファイル等で変更可能にします。
実行ユーザーを変更する際はOS上の権限・常駐サービスの設定も必要になるため、設定ファイルだけで権限を変更できるとは扱いません。

OS別の具体的なデフォルト値、設定ファイルの形式・配置・反映タイミングは未確定です。
既存の実行要求に含まれるコマンドや作業ディレクトリと端末設定の優先順位も、API設計時に確定します。
共通の実行制御値は[実行制御詳細設計](040_execution_control.md)を参照します。

## 重複防止と再実行

- 実行IDと処理状況をローカルに永続化し、要求の再配信やエージェント再起動後も二重実行を防ぎます。
- 受付済み・実行中のIDを再受信しても、新しいプロセスは起動しません。
- 完了済みのIDを再受信した場合は、保存済み結果の照合対象とし、バッチ自体は再実行しません。
- 再起動後に成否を確認できない処理は結果不明とし、自動再実行しません。
- バッチの再実行はサーバ側が判断し、元の要求とは別の新しい実行IDを発行します。
- 未送信結果の保持期限到達による削除で、同じ実行IDが再実行可能にならないようにします。

重複防止記録の保存形式・保持期間と、古い要求を拒否する仕組みは未確定です。
保存済み結果が存在しない場合も、結果を推測して成功・失敗として返してはいけません。

## 実行結果

| 項目 | 内容 |
| --- | --- |
| Execution ID | 対象バッチ実行要求の識別子です。 |
| Status | バッチの終了状態です。 |

## 追加合意: 添付ファイルを使用する実行

以下は添付機能の実装済み仕様であり、上記の一般的な作業ディレクトリ設定より優先する。

実行IDごとの専用ディレクトリへ確定済み添付を相対パスで配置し、そのディレクトリを実行開始位置にする。スクリプト自体も配布対象に含め、定義の実行コマンドでインタープリターと相対パスを指定する。
全ファイルの取得・配置・サイズ・SHA-256検証が成功してから起動する。準備失敗時はスクリプトを開始せず、その理由を報告する。固定ディレクトリの作成が必要な場合はスクリプト側で処理する。
作業領域はサーバーのバッチ共通設定から要求作成時に記録された保持期間を適用し、成功・失敗とも終了確認後から計測する。実行中・停止確認不能の領域は削除しない。結果JSON・再送記録・重複防止記録は作業領域の外へ保存する。

初期値と設定変更時の扱いの正本は、バックエンド設計リポジトリ
`0001-docs-smarthomewebserverbackend` の
`docs/02_SystemDesign/バッチ管理/Details/0005_batch_file_transfer_detail_design.md` 内
「定義添付ファイルとバッチ共通設定の合意仕様」とする。


実装では開始受理後のファイル準備もタイムアウトと同時実行数に含める。取得中もキャンセル可能で、全ファイル検証後にのみOSプロセスを起動する。
work/{executionId}は新規作成のみとし、既存領域を再使用しない。終了確認とcleanup_afterを実行記録へ保存し、結果送信・結果保持期限とは独立して回収する。通常周期と起動後の回収はos.Root配下に限定する。
旧要求（保持日数スナップショットなし）は従来の作業ディレクトリ指定を維持する。
